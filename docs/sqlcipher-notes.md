# SQLCipher 集成要点（验证原型阶段的实测记录）

本文件记录容易踩坑、且踩错后果严重（可能造成数据泄漏或丢失）的实现细节。
**不是教程**，是"施工须知"。

## 1. 不能用 Tauri 官方 SQL 插件

官方 `tauri-plugin-sql` 的模型是「前端把 SQL 字符串发给后端」。而加密数据库的密钥
必须留在 Rust 侧、绝不能出现在前端 JavaScript 里。两者设计目标冲突，官方插件至今
不支持 SQLCipher（见 tauri-apps/plugins-workspace#2528）。

**结论**：数据访问层自己写在 Rust 里，前端只调用你定义的 Tauri command
（如 `list_entries(year, month)`、`search_entries(keyword)`）。
前端永远拿不到密钥，也拿不到执行任意 SQL 的能力。

## 2. 静态编译：用户机器上什么都不用装

```toml
rusqlite = { version = "0.40", features = ["bundled-sqlcipher-vendored-openssl"] }
```

这个 feature 展开为 `bundled` + `bundled-sqlcipher` + vendored openssl，把
SQLite/SQLCipher 和 OpenSSL 一起静态编译进二进制。代价是首次编译慢，收益是
**分发时不需要任何运行时依赖**（不需要 DLL、不需要系统装 SQLCipher）。

Windows 上编译它需要：MSVC（C 编译器）、perl（OpenSSL 的 Configure 脚本）、
nasm（汇编优化）、make。见 `scripts/env.ps1`。

⚠️ **nasm 用 2.x 而不是 3.x**。OpenSSL 3.x 的汇编源码对 nasm 3 的新语法存在兼容性
问题，Strawberry Perl 自带的 2.16.01 是稳妥选择。

## 3. 密钥设置必须是连接后的第一条语句

```rust
let conn = Connection::open(&db_path)?;
conn.pragma_update(None, "key", format!("x'{}'", hex(&key)))?;
// 之后任何查询才会触发密钥验证
```

两个要点：

- **`PRAGMA key` 必须是第一条语句**。在它之前执行任何其他 SQL，SQLite 会先以
  明文方式创建/读取文件头，之后再设密钥也无法加密已有内容。
- **用 `x'...'` 十六进制形式传密钥**，不要用字符串拼接。原始密钥是 32 字节二进制，
  直接转字符串会引入转义和编码问题。

## 4. 不存第二份密码校验值

SQLCipher 自己会验证密钥：密钥不对时，`PRAGMA key` 之后的**第一条查询**就会失败。
所以判断"密码是否正确"的方式就是——试着执行一次查询。

**不要**再存一份密码哈希或校验值。多存一份就是多给攻击者一个离线爆破的目标，
而且它和真实密钥之间的一致性还得自己维护。

```rust
// 判断密码是否正确，就是这么简单
match conn.query_row("SELECT count(*) FROM entry", [], |r| r.get::<_, i64>(0)) {
    Ok(_)  => { /* 密码正确，进入应用 */ }
    Err(_) => { /* 密码错误，停留在解锁页 */ }
}
```

## 5. 密钥派生与内存清理

- 算法：**Argon2id**（`argon2` crate），绝不用 MD5/SHA 系列，绝不自己实现。
- salt：至少 16 字节随机数，**持久化在数据库文件旁边**（明文）。salt 不是秘密，
  但必须每次安装都不同，否则预计算攻击可行。
- 参数：内存开销建议 256 MiB 起，用实测校准（目标单次派生 500~1000 ms）。
  参数本身也要持久化，否则以后升级参数会导致老用户无法解锁。
- 派生完成后立即 `key.fill(0)` 清零内存中的密钥材料。

## 6. 锁定期状态必须放在加密库之外

用户**没解锁时**也要能读写信封（否则无法显示"还剩几次机会"、无法记录锁定截止时间）。
所以失败次数和锁定时间存在数据库之外的明文文件里。

⚠️ 由此产生一个必须在 UI 上说清楚的事实：**提示信息（hint）是明文可读的**，
因为它在锁屏界面就要显示。所以提示要写得模糊（"和你常用的数字有关"），
不能写成能直接推出密码的内容。

⚠️ 另一个必须让用户知道的事实：**锁定期挡不住离线爆破**。攻击者拿到数据库文件后，
可以在应用之外无限次尝试，完全不经过你的锁定逻辑。6 位数字只有 100 万种组合，
真正的防线是 Argon2id 的高内存开销（每个候选都要付 256 MB 内存 + 秒级时间）。

## 7. FTS5 中文搜索

SQLite 的 FTS5 默认 tokenizer 对中文无效（会把整句当成一个 token），
必须引入中文分词方案。候选：

- `simple` / `sqlite-fts-simple`：支持中文（简繁）+ 拼音的 FTS5 tokenizer，
  还能支持用拼音搜汉字。
- 若引入外部 tokenizer 成本过高，退路是在写入索引前用 `jieba-rs` 分词，
  把分词结果作为独立字段喂给 FTS5；代价是索引体积增大、需要维护分词一致性。

⚠️ **外部内容 FTS 表（`content='entry'`）不会自动同步**，必须建
`INSERT` / `UPDATE` / `DELETE` 三个触发器，否则新写的日记搜不到。
原型已验证这一点。

## 8. 一天一篇靠数据库约束，不靠应用逻辑

```sql
entry_date TEXT NOT NULL UNIQUE
```

不要用"先查有没有、再决定插入"的应用层判断 —— 一旦出现并发或异常路径，
就会产生两条同日记录，而这种脏数据清理起来非常麻烦。让数据库去挡。

同时 `entry_date`（逻辑日期）要与 `created_at`（实际写入时间）分离，
这样用户补写昨天的日记时，不会污染"这条是什么时候写的"这个事实。

## 9. 备份：SQLite 在线备份 API 不可用（实测）

**这是一个反直觉的坑，实测才发现。** 加密数据库不能用 SQLite 的
在线备份 API（`rusqlite::backup::Backup` / `sqlite3_backup_*`）：

```
backup is not supported with encrypted databases
```

SQLCipher 主动禁用了它 —— 该 API 在分页复制时还会复制每个数据库页的
元数据（编码格式、页大小、保留字节），而密钥/盐并不在其中，
所以复制出来的文件无法解密，SQLCipher 选择直接拒绝而不是给出坏结果。

**因此备份必须改用其它路径**（实测方案见
`app/src-tauri/examples/backup_probe.rs`）：

| 方案 | 做法 | 评价 |
|---|---|---|
| **VACUUM INTO 'path'** | 一条 SQL 让 SQLite 重写到新文件 | ✅ 采用。产物沿用当前连接的密钥，是密文；无需关闭连接 |
| WAL checkpoint + 复制主文件 | `PRAGMA wal_checkpoint(TRUNCATE)` 后普通文件复制 | 可行退路。必须先确认 `busy = 0`（无其他连接占用），否则可能复制到不一致状态 |
| 关闭连接后复制 | 最保守 | 影响正在使用的界面，不适合自动备份 |
| ~~在线备份 API~~ | — | ❌ 加密库上直接报错 |

⚠️ **WAL 模式让"裸复制文件"也不安全**：开了 WAL 后，最近的提交可能还在
`-wal` 文件里，只复制 `diary.db` 会丢掉这部分数据（甚至复制到撕裂的页）。
必须先 checkpoint。

⚠️ **备份必须连同 `crypto_meta.json` 一起保存**。它包含 salt 与 KDF 参数，
没有它即使有正确的 PIN 也派生不出密钥 —— 备份文件将永久无法打开。
这是最容易忽略、后果最严重的一点。

## 10. 附件不加密的已知风险（用户已确认接受）

正文有 SQLCipher 保护，但附件是明文文件。必须做两件事降低风险：

1. 附件存到**应用数据目录下的子目录**，不要放桌面或文档根目录。
2. 在设置页明确提示：**图片可能比正文更敏感，且云同步软件会把它们一起带走**。

数据库里只存**相对路径**。绝对路径在用户换电脑、改用户名、移动数据目录时全部失效。
