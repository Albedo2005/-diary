## V1：所见即所得编辑器（形态 C，像 Word 一样）

### 用户需求

> 写日记时看到的就是最终排版效果，不要看到 Markdown 语法符号。
> 打 `# 标题` 立刻变成大标题，`**加粗**` 立刻变粗，星号不出现。

### 状态

- **当前版本（P0）**：形态 A —— Markdown 源码 + 语法高亮，外加一键切换的阅读模式
- **V1**：升级为形态 C
- **预估工作量**：20~25 人日

### ⚠️ 关键架构约束（现在就必须遵守，否则升级不"平滑"）

**存储格式必须始终是 Markdown 原文，绝不改成 HTML 或富文本 JSON。**

这是整个升级方案能否平滑的唯一决定因素：

| 做法 | 后果 |
|---|---|
| **存 Markdown 原文** | ✅ 升级只是换编辑器组件。老数据天然兼容，导出、搜索、备份全部不受影响 |
| 存 HTML / 富文本 JSON | ❌ 要么写双向转换（极易丢格式、丢内容），要么迁移全部历史数据（有损坏风险） |

所以 P0 就要定下这条铁律：

- 数据库 `entry.content_md` 存 **Markdown 纯文本**
- 编辑器的所见即所得体验，是**在内存里把 Markdown 渲染成富文本、编辑后再转回 Markdown**
- 阅读模式用的渲染器与编辑器共用同一套 Markdown 解析逻辑

**风险提示**：Markdown ↔ 富文本的往返转换是 V1 的主要技术风险。
它可能出现"编辑一次后格式微妙变化"的问题（如列表缩进、空行数量）。
V1 必须包含**往返一致性测试**：对同一份内容反复转换 N 次，结果必须稳定。

### V1 的额外范围

| 项目 | 说明 |
|---|---|
| 富文本编辑器组件选型 | 需评估（TipTap / ProseMirror / Lexical 等），并验证中文输入法兼容性 |
| Markdown ↔ 富文本双向转换 | 核心风险点，需要大量测试 |
| 中文输入法（IME）组字不打断 | **当前版本明确延后**，V1 必须一并解决 |
| 粘贴处理 | 从网页/Word 粘贴时保留还是剥离格式，需要产品决策 |
| 快捷键 | Ctrl+B 加粗等 |

### 依赖关系

- 依赖 P0 的 Markdown 渲染器（阅读模式复用）
- 依赖 P0 确定"存储格式为 Markdown"这条约束

## V2：多日记本（用户按需增删）

### 用户需求（原话整理）

> 希望可以按照用户需求主动添加或者删除日记本的板块。
> 比如学生没有工作日记，就不需要这一块；有的人不在意美食，就不需要美食日记。

### 状态

- **当前版本（P0）**：单一日记本，但**建表时就加上 `notebook_id` 字段**
- **V2**：支持用户自由创建/删除日记本
- **预估工作量**：5~8 人日（详见下方分解）

### 为什么现在不做

多日记本看起来只是"多一张表"，但它会**渗透到每一个界面**：

| 受影响的模块 | 具体变化 | 人日 |
|---|---|---|
| 数据模型 | 唯一约束从 `entry_date` 改为 `(notebook_id, entry_date)` | 0.5 |
| 日记本 CRUD | 创建、重命名、改图标、删除（含数据处置） | 2 |
| 日记本切换器 | 侧栏或顶栏的切换 UI | 1 |
| 日历界面 | "今天写了没"变成"**这个本子**里今天写了没" | 1 |
| 搜索 | 需要决定：搜当前本子，还是全部本子（还要加筛选器） | 1 |
| 统计 | "连续写作天数"按本子算还是按总天数算 | 1 |
| 删除语义 | 删本子时里面的日记怎么办（一并删？移到回收？） | 1 |
| **合计** | | **5~8** |

**真正的成本不在开发，而在于它会让 P0 的每个界面都要多一层状态。**
先把单本体验打磨好，再引入这一层，是更稳的顺序。

### 现在必须做的预留（成本约 10 分钟，省掉将来的数据迁移）

建表时就带上 `notebook_id`，固定填默认本子的 id：

```sql
CREATE TABLE notebook (
    id         INTEGER PRIMARY KEY,
    name       TEXT    NOT NULL,
    icon       TEXT,
    sort_order INTEGER NOT NULL DEFAULT 0,
    created_at TEXT    NOT NULL
);

-- 默认本子，初始化时插入一行
INSERT INTO notebook (id, name, icon, sort_order, created_at)
VALUES (1, '我的日记', 'book', 0, <now>);

CREATE TABLE entry (
    id          INTEGER PRIMARY KEY,
    notebook_id INTEGER NOT NULL DEFAULT 1 REFERENCES notebook(id),
    entry_date  TEXT    NOT NULL,
    ...
    -- 现在：单本模式，用这个约束保证"一天一篇"
    UNIQUE (entry_date)
    -- V2 升级时改为：
    -- UNIQUE (notebook_id, entry_date)
);
```

这样 V2 升级只需**改唯一约束 + 加界面**，**不需要迁移任何历史数据**。

### V2 需要一并想清楚的产品问题

| 问题 | 选项 |
|---|---|
| 日记本是否有"模板/类型" | 例如"工作日志"预设了不同字段（任务、耗时）；"美食日记"预设了评分、地点 |
| 是否允许同一天在多个本子里各写一篇 | 允许（工作日志和生活日记可以同一天）—— 这也是多本的核心价值 |
| 删日记本时数据怎么处置 | ① 一并删除（需二次确认）② 移到"未分类" ③ 导出后删除 |
| 新建本子的默认集合 | 给一组预设让用户勾选（生活/工作/学习/读书/美食…），而不是让用户从空白开始 |
| 跨本子搜索 | 需要"全部本子"选项 |

**其中"日记本模板/类型"值得单独评估**：如果不同类型的本子字段不同，
数据模型会引入自定义字段的复杂度（EAV 或 JSON 列），工作量会显著上升。
建议 V2 先做"仅名称+图标不同"的轻量版本。

### 依赖关系

- 依赖 P0 的 `notebook_id` 预留字段
- 依赖 P0 的日历、搜索、统计三个界面（都要增加"本子"维度）

## V3+：其他已记录但未排期的想法

| 功能 | 备注 |
|---|---|
| 附件加密 | 当前决定不加密（用户已知风险）。迁移路径需预留：附件表已有 `sha256` 与相对路径，可平滑加解密 |
| 天气自动记录 | **与"完全离线"定位冲突**，需要用户明确同意联网才能做 |
| 导出 PDF | 需要渲染引擎，体积与排版质量需权衡 |
| 自动更新 | 需要签名证书 + 托管；国内网络可达性需考虑 |
| 代码签名证书 | 非技术问题（成本几百到几千元/年），正式分发前再办 |
| 拼音搜索 | 需引入支持中文+拼音的 FTS5 tokenizer（如 `simple` 扩展） |
| 标签自动建议 | 基于已有标签与分词结果推荐 |
