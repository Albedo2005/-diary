## 一、基础能力（全部通过）

环境：Windows，Rust 1.98.1 + MSVC 14.37，SQLCipher 由 rusqlite 的
`bundled-sqlcipher-vendored-openssl` 从源码静态编译。

| 验证项 | 结果 |
|---|---|
| SQLCipher 静态编译 | ✅ SQLCipher 4.14.0 community，**零运行时依赖** |
| 文件层加密 | ✅ 库文件中未发现明文汉字（不是只设了个开关） |
| 正确密码解锁 | ✅ 读到数据 |
| 错误密码解锁 | ✅ HMAC 校验失败被拒绝 |
| `ENABLE_FTS5` | ✅ = 1，不用改编译参数 |
| 一天一篇唯一约束 | ✅ 同日第二条被数据库拒绝 |
| 首次编译耗时 | 11 分 42 秒（一次性成本） |

**错误密码的实测表现**很有说服力：用改了一位数字的 PIN 派生密钥后，
SQLCipher 报 `hmac check failed for pgno=1` / `error decrypting page 1`。
这说明**它自带密钥验证，不需要我们再存一份密码校验值**。

## 二、中文全文搜索：方案对比

**已确认的硬事实**：FTS5 默认 tokenizer 对中文等同失效。实测搜「火锅」「开心」
「书」全部无结果。

| 方案 | 火锅 | 开心 | 日落 | 牛肉面 | 索引体积 | 结论 |
|---|---|---|---|---|---|---|
| **jieba 预分词** | ✅ | ✅ | ✅ | ✅ | 28 KB | **采用** |
| trigram（内置） | ❌ | ❌ | ❌ | ✅ | 48 KB | 否决 |

**否决 trigram**：2 字词（火锅/开心/日落/加班）是中文日记高频查询词，全部搜不到，
且索引体积反而更大。

**jieba 表现超出预期**：连「牛肉面」「聊到」这类词都切对了，7 个查询词全中，
索引建立 5 条仅 11.6 ms。

## 三、两个关键坑（本报告最有价值的部分）

### 坑 1：unicode61 不把汉字当分隔符

实测：`今天去吃了火锅。` 在 unicode61 下是**一个 token**。因此

- 搜「测试」✅ 命中（"测试"恰好在句首 token 边界）
- 搜「火锅」❌ 失败（不在 token 边界）

这个现象极具迷惑性 —— **它看起来像"搜索能用"，实际上大部分查询词都搜不到**。
诊断程序 `bin/trigger_diag.rs` 把库里实际内容打出来才定位到：
触发器写入正常，问题在分词。

**推论**：索引里必须是分词后的文本，存原文等于中文搜索失效。

### 坑 2：传统 FTS5 delete 命令对文本一致性极度敏感

`INSERT INTO fts(fts, rowid, seg) VALUES('delete', old.id, old.seg)`
要求提供的旧文本与索引内容**完全一致**，否则报 `SQL logic error`。

实测中我仅仅因为手打的 seg 与 jieba 切法差一个 token 就触发了该错误。
这意味着存储的分词文本一旦与索引漂移（分词器升级、数据迁移、手工改库），
UPDATE/DELETE 就会失败，严重时索引损坏。

**解法**：`contentless_delete=1`，删除只需 rowid，不需要重新提供原文。
实测孤儿行数 = 0。

## 四、最终定案（详见 `schema-decisions.md`）

| 决策 | 选择 | 关键理由 |
|---|---|---|
| FTS 表类型 | contentless (`content=''`) + `contentless_delete=1` | 免疫文本漂移；省一份文本副本 |
| 索引数量 | **两张**：jieba 词索引 + 单字兜底索引 | 实测「牛肉」只被字索引命中 |
| 索引同步 | Rust 侧写入时同事务更新 | 触发器无法调用 jieba |
| 结果高亮 | 在**原文**上做子串匹配 | 实测 FTS5 的 highlight 输出含分词空格，直接展示排版破碎 |
| 分词方案 | jieba | trigram 无法处理 2 字词 |

## 五、KDF 参数（本机实测）

| 参数 (m / t / p) | 耗时 | 评价 |
|---|---|---|
| 64 MiB / 3 / 1 | 83 ms | 偏快 |
| 128 MiB / 3 / 1 | 167 ms | 偏快 |
| 256 MiB / 3 / 1 | 379 ms | 略快 |
| **512 MiB / 3 / 1** | **792 ms** | **★ 采用** |
| 1024 MiB / 3 / 1 | 1693 ms | 过慢 |
| 512 MiB / 2 / 1 | 546 ms | 备选（对低配机器更友好） |

**建议实现自适应校准**：安装时从 64 MiB 起逐步加倍并计时，直到进入 500~1000 ms
或触及上限，再把最终参数写进数据库。这样同一份程序在高低配机器上都合适。

⚠️ **参数必须持久化并在解锁时读取，绝不能硬编码**，否则调整参数会导致老用户
无法解锁自己的日记。

## 七、踩过的坑（给未来的自己）

1. **vendored OpenSSL 在 Windows 上必须有 perl**，否则编译直接失败。
   nasm 用 2.x 而非 3.x —— OpenSSL 3.x 汇编源码对 nasm 3 新语法兼容性有风险。
2. **Windows PowerShell 5.1 把无 BOM 的 UTF-8 脚本按 GBK 解析**，
   中文注释会导致语法错误。项目里的 `.ps1` 一律写成纯 ASCII。
3. **GitHub 直连在本机不可用**（TLS 连接被中断），改用 `ghproxy.net` 镜像。
4. **移动 `CARGO_HOME` 会让 Cargo 指纹全部失效**，所有 C 依赖
   （SQLCipher + OpenSSL）要重编，约 11 分钟。一次性代价，但要提前知道。
5. **不要改 `CARGO_TARGET_DIR`**：只要与上次构建的值不同就触发全量重编。
6. **PowerShell 里 `$` 会被变量展开**，会静默破坏传给程序的字符串。
   调试 SQL 字符串时优先把输出写进文件而不是靠管道。
7. **测试本身可能有缺陷，得出错误结论**。本次有三次"发现"实际是测试写错：
   - 用 `count(*)` 测外部内容表同步 → 无效（外部内容表不存文本，count 走内容表）
   - 字索引查询走了 jieba 分词 → 查的是整词，导致误判字索引无效
   - 手打 seg 值与 jieba 不一致 → 触发删除报错
   **教训：结论反常时先怀疑测试，并且用两种独立方式互相验证。**
