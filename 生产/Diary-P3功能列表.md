### 2.2 "可扩展"是什么（你要听的那部分）

**一句话**：可扩展 ＝ **"以后想加东西时，要动的地方少，而且漏了会立刻发现"**。

它**不是**"把代码重写一遍"，而是解决**一个具体的疼**：

| 现在的疼 | 具体到什么程度 |
|---|---|
| **加一条新功能要改四个地方** | 有一处没改，**编译器不报错** —— 只是功能"悄悄不生效" |
| **最大的那个文件装了后端的三分之二** | 8,155 行；找一处 SQL 只能靠搜索 |
| **三个界面文件大到看名字猜不到内容** | 写日记那屏 2,896 行、设置页 1,954 行、主界面 1,616 行 |

**为什么它值得排在功能前面**：P3-1 / P3-2 要动统计页，P3-3 要引 3D 引擎，P3-4 要动全局外观 ——
这三件**都会撞上同一批"不好改的地方"**。地基先垫平，后面每件都省；反过来，每做一件都在原地绕一次。

**⚠️ 但有一条必须说清楚**：可扩展**本身不会让你看到任何新东西** —— 它只让"以后改起来便宜"。

### 2.3 "可扩展"的三种做法（代价差很多，这是要你挑的）

| 做法 | 干什么 | 代价 | 你能看到什么 |

| **① 只加"自动检查"** | 写一个脚本：后端命令 ↔ 前端通道**对不上就报红** | 半天量级、**不碰产品代码、不动发布件** | 什么也看不到，但**从此不会再"加一条功能埋一颗雷"** |
| **② ① ＋ 把"导出 / 备份 / 恢复"搬出大文件** | 只搬这一类，**行为零改动** | 要**重跑全量测试**（15~20 分钟） | 看不到 |

### 2.4 ⭐ 方案①「只加自动检查」到底做什么（你点名的部分）

**一句话**：写一个**离线脚本**，把「**后端登记的命令**」和「**前端能调的通道**」两张表**对一遍**，
对不上就**报红** —— 它只是**仓库里的一个工具**，⛔ **不进产品代码、不进安装包**
（你装的 `日记.exe` 里根本没有它）。

**① 检查哪些内容**（4 类，从最要紧到最松）

| 检查项 | 报什么 | 严重度 |
|---|---|---|
| 前端调了、后端**没登记** | "命令不存在，一运行就报错" | 🔴 **硬错误**（必须修） |
| 后端登记了、**谁都不调** | "这条命令是死的"（E1 那种） | 🟡 警告（多数要修，少数走白名单） |
| 前端封装了函数、**界面没人 import** | "功能做了一半"（E3 那 4 条） | 🟡 警告（可能是有意留的） |
| 命令名 / 文档里的名字**对不上** | 文档过期（D 组那种） | 🔵 提示 |

**② 触发时机**（建议挂三处 ＋ 一处"明确不做"）

| 时机 | 怎么挂 | 效果 |
|---|---|---|
| **手动** | 敲一条命令就跑（一个脚本） | 想查随时查 |
| **提交前** | 挂进提交流程，**不通过就不让提交** | 雷**在进仓库前**被拦下 |
| **发布前** | 打包脚本开头调一下，**红就不打安装包** | 雷**在出门前**被拦下 |
| ⛔ **不做** | **不在应用运行时检查** | 那是给用户装的东西，不该带开发期的检查 |

**③ 失败时怎么处理**

- 脚本**打印一张对照表**（哪条命令 / 哪类问题 / 在哪一行），并**以"失败"退出**
  —— 这样流程 / 打包脚本能把它当"没通过"。
- ⛔ **绝不自动改代码**：只报"哪里对不上"，**改不改、怎么改由人定**（有些是**故意**不接线的）。
- ⚠️ **能力边界（必须先讲清）**：它只能发现"**登记与调用对不上**"，**发现不了"逻辑写错"**
  —— 后者要靠测试。⇒ 它是**补丁**，**不是测试的替代品**。

**④ 不涉及哪些改动（这条你最该看）**

| 不碰的 | 为什么 |
|---|---|
| ⛔ **产品代码** | 脚本在 `scripts\` 里，够不着 `app/src/**` |
| ⛔ **版本号** | 还是 `3.16` |
| ⛔ **发布件** | `日记.exe` **逐字节不变** —— 脚本根本不进安装包 |
| ⛔ **268 条界面验收** | 界面一行没动，不用重跑 |
| ⛔ **全量测试** | 产品代码没动，不用重跑 |
| ⛔ **新依赖** | 用现成的 Node / PowerShell 就够 |

✅ **唯一的产物**：仓库里**多一个脚本 ＋ 一份白名单 ＋ 一行使用说明**。

⚠️ **唯一的代价（老实说）**：脚本要维护一份**"白名单"** —— 记下"这几条命令是**故意**不接线的"
（比如 E2 那 4 条后端自用的）。但这**恰恰是好事**：不写进白名单，脚本就报红；
写了，等于**留下一条"为什么"的记录** —— 把"**悄悄漂移**"变成"**必须说明**"。

### 「多日记本」到底是什么（你本轮问的）

**它是什么**：现在整个软件**只有一个日记本**，所有日记全放在这一个里。
"多日记本" ＝ **你自己开几个分开的本子** —— 比如「日常」「工作」「旅行」，
各写各的、互不打扰，可以**单独上锁、单独导出**。

**它现在的状态**（实测，不是推测）：

| 项 | 状态 |
|---|---|
| 数据库里"日记本"那张表 | ✅ **已经建好了**（字段：名字 / 图标 / 排序 / 创建时间） |
| 每篇日记上"属于哪个本子"那个字段 | ✅ **已经加好了**（老日记全部默认挂在 1 号本上） |
| 打开软件时的默认本子 | ✅ **已经自动建了一个，叫「我的日记」** |
| "一天最多一篇"这条约束 | ⚠️ **现在是"全局一天一篇"** —— 多本之后要改成"**每个本子各一天一篇**"（否则你在「工作」和「日常」里，同一天只能写一篇） |
| 界面上的本子切换 | ❌ **完全没有**（整个前端一行相关代码都没有） |

**所以"底子打好了"省掉了什么**：省掉了**数据迁移** —— 老日记不用搬、不用改。
**那它贵在哪**：贵在**"到处都要多问一句：现在看的是哪个本子"** ——
后端 **50 处**取数据的地方、前端 **11 个**界面文件，**每一处都得知道这件事**。
⇒ 这才是 5~8 人日的真正来源，**不是建表难，是"处处都要带上它"**。

**一句老实话**：这个功能**做起来不难，但摸到的地方最多** ——
也正因为如此，**越晚做越贵**（每加一个新界面，将来都要跟着补一遍）。
