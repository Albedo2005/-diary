## 0. 通用约束（每个功能都适用，AI 必须遵守）

### 0.1 项目结构（Tauri 2 + Vue 3）

| 位置 | 角色 |
|---|---|
| `app/src/**` | 前端（Vue 3 + TS）。组件只调 `api/index.ts`，不直接 `invoke` |
| `app/src/api/index.ts` | 前端调后端的**唯一出口**，每个后端命令一个封装函数 |
| `app/src-tauri/src/commands.rs` | 命令层（服务员）。只做参数校验 + 守门，业务甩给 `db.rs` |
| `app/src-tauri/src/db.rs` | 数据层（后厨）。所有 SQL 都写在这里 |
| `app/src-tauri/src/schema.rs` | 建表语句 + `SCHEMA_VERSION` |
| `app/src-tauri/src/crypto.rs` | 密钥派生、锁定期 |
| `app/src-tauri/src/lib.rs` | 启动 + 命令白名单（`generate_handler!`） |

### 0.2 铁律（违反即返工）

1. **新增一个命令，必须同步改三处**，漏一处就调不通：
   1. `db.rs` 加实现方法（真正的 SQL）
   2. `commands.rs` 加 `#[tauri::command]` 函数
   3. `lib.rs` 的 `tauri::generate_handler![...]` 里登记
   4. `app/src/api/index.ts` 加封装（前端才用得上）
2. **凡是要碰数据的命令，必须用 `with_vault(&state, |v| ...)` 包住**（未解锁时统一拒绝）。例外只有：`app_status`、`estimate_kdf_ms`、`initialize_vault`、`unlock_vault`、`lock_vault`。
3. **前端永远不接触密钥**，也不传 SQL。只传业务参数（日期、文本、id）。
4. **"有没有写过"只有一个判定来源**：`db::has_content_sql()`（SQL 侧）和 `db::has_content()`（Rust 侧）。任何新功能要判断"这天写过没"，必须调它俩，**不许自己写 `content_md != ''`**。
5. **一天一篇靠数据库 `UNIQUE(entry_date)`**，写库一律用 `INSERT ... ON CONFLICT(entry_date) DO UPDATE`，**不许"先查再插"**。
6. **错误必须带稳定的 `kind` 字段**（前端按 `kind` 分支，不解析 message 文本）。已有 kind 见 `AppError`；新增场景要复用已有 kind，别造字符串。
7. **改 `.vue`/`.rs`/`.ts` 源文件不要用 PowerShell 文本替换**（会把 UTF-8 中文注释变成乱码，本项目已出过事故）。用编辑器/文件写入工具。
8. **不要动**：`entry.content_md` 永远是 Markdown 原文（V1 所见即所得依赖这条）；`notebook_id` 字段必须保留（V2 多日记本依赖）。

- `tag` / `entry_tag` 表**已建好**（schema.rs 第 118–127 行），但没有对应的 Rust 代码
- `attachment` 表**已建好**（schema.rs 第 137–147 行），但没有对应的 Rust 代码
- `app_setting(key, value)` 通用键值表**已建好**，可存任意设置项

  而 `core:window:default` **只授读权限**（`allow-is-fullscreen` / `allow-is-maximized` 有，
  `allow-set-fullscreen` / `allow-maximize` / `allow-unmaximize` / `allow-center` 都没有）。
  这与下面那条"明确不做窗口模式"是一致的：应用**不碰窗口状态**。
  ⚠️ 将来若真要加"改窗口"的功能：权限缺失是**运行时**才报错的，编译期完全看不见 ——
  编译通过 ≠ 这个功能能用。
- 窗口参数在 `app/src-tauri/tauri.conf.json`：1040×720、最小 720×520、`center: true`。
  `center` **只在首次创建窗口时生效**。窗口的大小、位置、最大化全交给系统标题栏，应用不管。
- 🚫 **明确不做「窗口模式」与「记住窗口几何」**（2026-09-20 用户撤销）。
  这两条曾作为功能 12 / 13 完整设计过、也实现过（版本 1.8），并在同日被否掉：
  用户原话"**我写日记也不需要沉浸式**"。撤销理由：全屏对日记应用没有价值；
  而只留"窗口 / 最大化"两档同样没意义 —— 系统标题栏本来就有那两个按钮。
  随之一起删掉的还有库外偏好文件 `data/ui_prefs.json` 与那四条窗口权限。
  **不要再提议做这个功能**（设计文档里已无对应章节，也别"补回来"）。
- `Stats` 结构已有 `total_entries / total_words / streak_days / first_date / last_date`
- 备份能力已有：`Vault::run_backup()`（内部 `VACUUM INTO`）、`backup_to()`

>
> 1. **"只能在写过的日记上打标签"做成了两层**。文档只写了"界面置灰"，
>    但界面置灰拦不住任何东西（排队中的自动保存、将来别的调用路径）。
>    后端也设了硬闸：按 `has_content_sql()` 判定，**必须已有正文**，否则返回

>    否则只能凭空插空行 → 破坏"打开 ≠ 写过"），只是**从"提示"升级成"约束"**

> 2. **已锁定的日记拒绝改标签**（文档没提）。锁定 = 只读，标签也是这篇日记的一部分，
>    与 `save_entry` / `delete_entry` 同一口径。只读不受影响。
> 3. **三个方法的返回值比文档多**：
>    `set_entry_tags` 返回**库里那份**标签名（清洗规则在后端，前端自己算必然差一点）；
>    `rename_tag` 返回清洗后的最终名字（撞名时仍是 `validation` 错误）；
>    `delete_tag` 返回**受影响的关联数**（界面靠它说清"3 篇日记的标签没了，内容没动"——
>    不说这句，用户看到"已删除"第一反应就是"我的日记呢"）。
> 4. **去重只折 ASCII 大小写**（`to_ascii_lowercase()`），不是 `to_lowercase()`。
>    `tag.name` 是 `UNIQUE COLLATE NOCASE`，而 SQLite 的 NOCASE **只折 A~Z**；
>    用 Unicode 的 `to_lowercase()` 范围更大，会造成"应用认为重名、数据库认为不重名"。
> 5. **`SearchPanel` 没动，列表展示放在 `CalendarPanel` 侧栏**，并且**多给了改名/删除入口**
>    （✎ / ✕）。原因：那两个后端能力是本次交付的一部分，没有入口就是**死代码**，
>    "删标签后日记内容完好""重命名撞名要报错"两条验收也**没法亲手验**。
>    按标签**筛选仍然没做**（文档写了留到后面）。侧栏 268px 宽，标签列表自己滚动。
>
> ⚠️ **本项唯一没在真机上验的还是 GUI 链路**：标签区在真实窗口里的样子、
> 下拉候选的位置与点击手感、侧栏改名输入框的焦点行为。沙箱起不了 GUI 进程，
> 必须双击 `发布\日记.exe` 用人眼过一遍。
>
> ⚠️ **一个刻意的"不做"**：撤掉某篇日记的标签**不会**顺手删掉"没人用的标签行"。
> 清理是显式动作（`delete_tag`）。自动删会产生"我撤了 A 篇的标签，B 篇上的同名标签
> 也没了"这种看不懂的行为。代价是库里会留 0 篇的标签 —— 所以 `list_tags` 用
> **两层 LEFT JOIN** 让它们照常出现在列表里（藏起来用户就没机会删它了）。

### 目标
给日记打标签，支持按标签筛选。

### 数据结构（已就绪，不用改表）
```sql
tag(id, name UNIQUE COLLATE NOCASE)
entry_tag(entry_id, tag_id, PRIMARY KEY(entry_id, tag_id),
          FK entry_id → entry(id) ON DELETE CASCADE,
          FK tag_id   → tag(id)   ON DELETE CASCADE)
```
`ON DELETE CASCADE` 的方向是对的：**删标签只删关联行，不会删日记**。

### 后端要加的（`db.rs`）
| 方法 | 作用 |
|---|---|
| `list_tags() -> Vec<TagStat>` | 所有标签 + 每个标签的日记篇数（只数"写过的"） |
| `tags_of_entry(date) -> Vec<String>` | 某天日记的标签 |
| `set_entry_tags(date, tags: Vec<String>)` | 整组覆盖：算差集，删掉多余的、插入新增的（在同一事务里） |
| `rename_tag(id, new_name)` | 改名。**若新名字已被别的标签占用 → 返回 `validation` 错误，不合并** |
| `delete_tag(id)` | 删标签（关联行随之删，日记不受影响） |

`commands.rs` 对应加 5 个命令（走 `with_vault`），`lib.rs` 登记，`index.ts` 封装。

### 前端要加的
- `EditorPane.vue` 标题下方加一行标签区：已有标签以 chip 显示（点 × 删除），末尾一个"＋"输入框，输入时下拉提示已有标签。
- `SearchPanel.vue` 或 `CalendarPanel` 加标签筛选入口（P1 可先只做"列表展示"，筛选放 P2）。

### 关键设计与坑
1. **只能在"写过"的日记上打标签**。理由：`entry` 行是通过 `save_entry` 的 upsert 产生的，标签要挂到 `entry_id` 上。若日记还没内容（`id = 0`），此时打标签要么插空行（破坏"打开 ≠ 写过"原则）、要么失败。**做法：内容为空时标签区置灰并提示"先写点内容"**。
2. **插入标签必须两步**：`INSERT OR IGNORE INTO tag(name) VALUES(?)` → `SELECT id FROM tag WHERE name = ?`。不能假设 `last_insert_rowid()` 一定有效（被 OR IGNORE 跳过时它是旧值）。
3. **标签名要清洗**：`trim()` → 空则忽略 → 限长（建议 20 字符）→ 去重（同一日记内不许重复）。
4. **重命名遇重名**：不要静默合并（用户会以为只是改名，结果两个标签的日记混在一起）。返回错误让用户自己决定。
5. **事务**：`set_entry_tags` 的"删 + 插"必须在同一事务，否则中途失败会产生部分更新的标签。

### 验收标准
- [x] 给某天加标签"旅行"→ 重新打开这天，标签还在 ← `tags_round_trip_across_reopen`（**重开整个库**，不只是重开这天）
- [x] 标签名重复输入"旅行"两次 → 只存一个 ← `duplicate_tag_names_are_stored_only_once`（还覆盖了只差大小写的 Travel/travel，并直接数了 `tag` 表行数）
- [x] 删标签"旅行"→ 标签消失，但所有打过该标签的日记**内容完好**（打开确认）← `deleting_a_tag_never_touches_entry_content`（逐项断言 title/content/stats/search，并查了搜索索引没被碰坏）
- [x] 重命名为已存在的标签名 → 报错，两个标签都保持原样 ← `renaming_onto_an_existing_name_is_rejected_and_changes_nothing`（含 NOCASE 撞名；断言的是**名字集合没变**，不是某个固定数字）
- [x] 给空日记打标签 → 界面不允许 ← `tagging_an_entry_without_content_is_rejected`（**两层都测**：前端置灰 + 后端硬闸；且断言被拒后 `tag` 表**一行都没多**）

### 增强 第 1 项（2026-09-20 追加 · ✅ 已实施 2026-09-21，提交 `23c8c7b`）：标签从"自由输入"升级为"列表选 + 自写"

> 用户原话："这个标签我希望加强一下做个列表，可以自主选择几个，然后也可以自己写，
> 自己写的列为其他就好。"
>
> **只改前端**：后端那 5 个方法、两张表**一行都不用动**
> —— `list_tags()` 正好提供了"其他"组要的候选。

#### 要解决的问题

现在（功能 1 已实施）的标签区是**纯自由输入**：想打什么字就打什么字。两个毛病：

1. **记不住自己有哪些标签** —— 想打"旅行"却打成"旅游"，库里于是多出一个名字不同、
   内容一样的标签，两个都只有一两篇。功能 1 给侧栏加了改名/删除，但那是**事后**补救。
2. **每次都要敲字** —— 常用的那几个标签本该一点就有。

#### 形态（已定）

点标签区的「＋」→ 弹出面板，**分三块**：

```
┌─ 标签 ─────────────────────────────────────┐
│ 常用                                      │  ← 前端常量；已在库里的呈"选中"态
│ [日常] [工作] [学习] [计划] [读书] [灵感] │
│ [反思] [家人] [朋友] [运动] [旅行] [假期] │
│ [美食] [健康]                             │
│                                           │
│ 其他                                      │  ← 用户自己写过的、不在预设名单里的
│ [失眠] [搬家]                             │
│                                           │
│ ＋ 输入新标签…                     [添加] │  ← 写完即归入上面的"其他"组
└────────────────────────────────────────────┘
```

- 点任意 chip → 选中 / 取消，**即时生效**（与现有的 × 删除同一手感）
- 已选标签仍然显示在编辑区的 chip 行上（点 × 可撤）
- 点面板外 / 按 `Esc` → 关闭
- **（2026-09-21 补）**「其他」组每个 chip 右侧还多一个 `×`，可就地删掉自己写错 / 不再想要的标签 —— 见下面「增强 第 2 项」。

#### 关键设计（照这个做，别自己发挥）

1. ⚠️ **"列为其他"是"分组显示"，不是"合并成一个叫『其他』的标签"。**
   这是最容易理解错的一条。把"旅行"和"失眠"都塞进同一个名为"其他"的标签里，
   两者就**再也分不出来了** —— 不可逆的信息丢失，而且与刚做完的"改名 / 删除"直接矛盾。
   **正确做法：只是把它们显示在第二组里，标签本身各自独立。**
2. ⚠️ **预设名单是前端常量，一行都不要写进库。** 只有用户**真正选中**的标签才进 `tag` 表。
   反例：启动时把 14 个预设标签 seed 进库 → 侧栏（功能 1 已做的标签列表）立刻冒出
   14 个"0 篇"的标签，把用户自己那几个挤到看不见的地方。
   附带好处：以后想改预设名单，**改一行常量**即可，不需要数据迁移。
3. **"其他"组的候选 = `list_tags()` 减掉预设名单** —— 不加新命令、不加新字段。
   `list_tags()` 返回的就是"库里真实存在的标签"，天然等于"用户自己写过的那些"。
4. **提交复用 `set_entry_tags(date, names)`（整组覆盖）**，不新增接口。
   前端维护"当前选中的名字数组"，每次变更整组提交。
5. **清洗规则一个字都别重写** —— `trim` / 20 字上限 / 同篇去重 / ASCII 大小写折叠
   全在 `db::normalize_tag_names` 里；前端**不要自己先洗一遍**（两套规则必然差一点）。
   前端只需把"用户敲了什么"原样送上去，再拿返回的"库里那份"刷新界面。

#### 坑

1. ⚠️ **并发覆盖 —— 本条最容易错的地方。** `set_entry_tags` 是**整组覆盖**语义。
   连着快点两个标签会发两个请求，**若乱序到达，后到的旧值会把新值盖掉**
   —— 表现为"我明明点了三个，最后只剩两个"。
   → 必须串行化：**上一次没回来之前不发下一次**（或只提交"最后一次"的最终状态）。
   **不要裸用 `Promise.all`。**
2. **浮层行为直接抄功能 9（日历快速跳转）的作业**：需要 `position: relative` 定位上下文、
   用 **`pointerdown` 而不是 `click`** 判"点外部关闭"（`click` 会和打开面板的那次点击打架）、
   `Esc` 关闭、**`onUnmounted` 里 `removeEventListener`**（否则反复挂载会累积监听器）。
   同一个项目里已经有这个坑的解法，**不要重新踩一遍**。
3. **输入法组字期间的回车不能当提交** —— 功能 1 的 `＋` 输入框已经处理过
   （`compositionstart` / `compositionend`），新面板沿用同一套判断。
4. **面板上 chip 的选中态要以"库里的状态"为准**，不要只改前端数组就画出来。
   与功能 1 的既定原则一致：**界面的最终状态来自数据库**，不是来自前端自己那条推理链。
5. **预设名单 14 个**（上面那排就是建议稿，**改一行常量即可**）：

   ```ts

     "日常", "工作", "学习", "计划", "读书", "灵感",
   ```

#### 要解决的问题

功能 1 的标签区只能**加**、不能**减（减掉"整库里的某个标签"）**：
面板「其他」组里每一个都是用户自己敲出来的，可是打错一个（想打"旅行"敲成"旅游"）
或过阵子不想要了，界面里**没有地方能删掉它** —— 只能专门跑去侧栏那处管理区删。
标签于是越积越多、越积越像，这正是用户说的"数据冗杂"。

#### 形态（已定）

「其他」组每个 chip 右侧多一个 `×`；点它**不直接删**，先在面板底部弹一条确认：

```
┌─ 标签 ───────────────────────────────────────┐
│ 常用 （预设名单，同第 1 项）                 │
│                                              │
│ 其他  [失眠 ×] [搬家 ×]                      │
│                                              │
│ ＋ 输入新标签…                [添加]         │
└──────────────────────────────────────────────┘

  ↑ 点「其他」组里某个 × 之后，面板底部多出一条确认：

  ┌────────────────────────────────────────────┐
  │ 移除标签「失眠」？它正被 3 篇日记使用 ——   │
  │ 移除后它不再出现在可选标签里，但那 3 篇    │
  │ 日记仍然保留它。                           │
  │                                            │
  │                             [移除]  [取消] │
  └────────────────────────────────────────────┘
```

#### 关键设计（照这个做，别自己发挥）

1. ⚠️ **两种 `×` 不是一回事，别混、更别合并成一个。**
   - 编辑区 chip 行上的 `×`（`removeTag`）＝ 把标签从**这一篇**上摘掉，标签还留在库里；
   - 面板「其他」组 chip 上的 `×`（`askDelete`）＝ 让标签**从可选列表里退休**
     （它不再出现在列表里，但**已写过的日记仍然保留它** —— 见第 3 项）。
   前者是日常编辑；后者改的是「以后还出不出现在可选列表里」，
   所以过一道确认 —— 但那是**防误触**，不是防「不可逆」。
2. ⚠️ **只有「其他」组带 `×`。** 预设名单是**前端常量**、根本没进库 ——
   没有可删的东西；「其他」里那些才是用户自己敲出来的。
   这条同时回答了"为什么同样一排 chip，有的带 × 有的不带"。
3. ⚠️ **执行前必须确认，且要写明"影响几篇 + 那些日记仍保留它"。**
   侧栏那处删除（功能 1）**刻意不确认**，因为它处在专门的管理区、动作单一；
   而这里那个 `×` 就贴在一排可点的 chip 旁边，误触的代价（一个常用标签从此
   从列表里消失）远大于多点一次的麻烦。
   篇数取 `TagStat.entry_count`（后端按"写过"统计，与日历标记同一条 `has_content_sql()`），
   **前端不要另算一份**。
4. ⚠️ **（已被第 3 项推翻，保留原文供对照）**
   当初要求「删掉的正是本篇挂着的那个标签」时，同步摘除前端的 `tags` / `syncedTags`。
   那是**硬删**下的补丁：库里的关联行没了，前端不清就会拿旧名单提交。
   改成软删除后关联行**还在**，这样做反而会让提交名单比库里少一个 ——
   **第 3 项已把它删掉**。
5. **`Esc` 的语义要分层**：确认条已弹出时按 `Esc` ＝ **撤掉确认**（用户多半在反悔），
   没弹时才关面板。一下把面板收走，会让人以为"刚才那一删执行了"。
6. **关闭面板 / 换日期都要清掉"待确认"** —— 不该让"上回没确认完"的问句留在屏幕上。
7. **不弹系统 `confirm()`**：它与这套界面风格无关；在面板里紧挨着那个 `×` 自绘一条，
   用户一眼就知道在确认什么。

#### 验收标准
- [ ] 面板「其他」组每个 chip 右侧有 `×`；「常用」组**没有**
- [ ] 点 `×` → 面板底部出现确认条，写明篇数与"正文不受影响"
- [ ] 点「取消」或按 `Esc` → 确认条消失，标签**还在**（没有删）
- [ ] 点「移除」→ 该标签从「其他」组、也从侧栏标签列表里消失
- [ ] **（第 3 项修订）**移除的标签正挂在本篇上时 → **chip 行上那个保留**（历史不动）
- [ ] **（第 3 项修订）**被 N 篇日记用着的标签移除后 → 那 N 篇**正文一字未改，标签也都还在**
- [ ] 点面板外 → 关闭，且"待确认"被清掉（再打开不会看到上回那条）

### 增强 第 3 项（2026-09-21 追加 · ✅ 已实施，提交 `bc6f984`）：标签删除改为**软删除**（不再改动历史日记）

> 用户原话："我的意思是这个标签对应的日记还是这个标签，但是这个标签使用的少了
> 或者不会再使用，把它删去比较节约地方，**而不是将以前的对应标签都删去**。"
>
> ⚠️ 这一项**推翻了第 2 项定下的语义**：第 2 项把「删除」实现成了**硬删**
> （`DELETE FROM tag`，关联行随 `ON DELETE CASCADE` 一起清掉），于是「删除」
> 会顺手改写历史日记。**这不是用户要的** —— 他要的只是"它别再出现在我眼前"。
>
> 这是本项目第一次**因为语义定错而返工**：当初把「删除 = 那几篇日记失去该标签」
> 写进了文档，用户当时没察觉，直到真的用上了才发现不对。
> 教训：**「删除」这种动词，必须当场问清"删的是哪一份东西"** ——
> 是删"字典里的条目"，还是删"历史记录上的那笔"。

#### 要解决的问题

第 2 项之后，「删除标签」这一个按钮里混着两件不同的事：

| 意图 | 用户想表达的意思 | 应该怎么落 |
|---|---|---|
| **A** | 这个标签我以后不想再用了 → **从可选列表里拿掉** | 本项要做的 |
| **B** | 把某个标签从**某一篇**日记上撤掉 | 编辑器 chip 行的 `×`（已有） |

第 2 项把 A 做成了「整库删 + 连坐清关联」，效果上顺带对**所有历史日记**做了 B。
用户发现后说："我希望的只是删标签，不是删以前的对应关系。"

#### 形态（已定）

界面**一个字都不用改**（还是那排 `×`、还是那条确认条），改的是**语义**与文案：

```
  ┌────────────────────────────────────────────┐
  │ 移除标签「失眠」？它正被 3 篇日记使用 ——   │
  │ 移除后它不再出现在可选标签里，但那 3 篇    │
  │ 日记仍然保留它。                           │
  │                                            │
  │                             [移除]  [取消] │
  └────────────────────────────────────────────┘
```

#### 数据结构（该动的都在这）

```
tag(id, name UNIQUE COLLATE NOCASE, retired INTEGER NOT NULL DEFAULT 0)   ← 加一列
entry_tag(entry_id, tag_id, PK)                                           ← 一行都不动
```

`SCHEMA_VERSION` **2 → 3**，升级分支在 `db::upgrade_from`（升级前照例先
`VACUUM INTO` 快照）。老库里的标签 `retired` 默认 0 = 在列表里 ——
**不能**让用户升级后发现"我标签全没了"。

#### 关键设计（照这个做，别自己发挥）

1. ⚠️ **「删除」= `UPDATE tag SET retired = 1`，不是 `DELETE FROM tag`。**
   这一个动词的差别就是全部：`entry_tag.tag_id` 上的 `ON DELETE CASCADE` 是**连坐**，
   真删会连带清掉"哪几篇日记用过它" —— 那正是用户不要的。
2. ⚠️ **`list_tags()` 要加 `WHERE retired = 0`，`tags_of_entry()` 千万不能加。**
   一个过滤、一个不过滤，正是「列表里看不见、日记上留得住」的全部实现。
3. ⚠️ **复活只在「新挂上」的那一次**（本项最容易写错的一条）。
   前端提交的是**整组**标签，所以一篇老日记只要被编辑一次，它身上那个退休标签
   就会出现在名单里。判据必须是"这次真的往 `entry_tag` 插进了一行"
   （靠 `INSERT OR IGNORE` 的返回值），**不是**"名单里有这个名字"。
   反过来，用户在**新的一篇**上亲手敲这个名字 = 明确要再用它 → 顺手复活。
4. ⚠️ **前端要删掉「同步摘除 `tags` / `syncedTags`」那段代码。**
   它是给硬删写的；软删除下关联行还在，再摘反而会让提交名单比库里少一个 ——
   那就真的把标签从这一篇上删掉了。
5. **命令改名 `delete_tag` → `retire_tag`**（四处：`db.rs` / `commands.rs` /
   `lib.rs` / `api/index.ts`）。名字必须诚实说明它做的事 ——
   叫 `delete` 会诱导后人写出会改历史的代码。
6. **确认条还留着**（第 2 项定的），但理由变了：不再是「防不可逆」，
   而是**防误触**（那个 `×` 就贴在一排可点的 chip 旁边）。
7. **幂等的含义变了**：重复调用不报错，但返回的仍是"挂着它的篇数"
   （关联行一直都在），不再是 0。

#### 代价（明说，不粉饰）

会出现一种新状态：**某篇日记挂着一个"列表里找不到的"标签**。
这是**故意**的 —— 用户要的就是"我不再用它了，但别动我写过的东西"。
要把它从某一篇上摘掉，走编辑器 chip 行的 `×`。

#### 验收标准
- [ ] 移除标签 → 它从侧栏标签列表与面板「其他」组里消失
- [ ] 但**已经贴过它的日记仍然显示它**（编辑器 chip 行还在）
- [ ] 那几篇日记的**正文、字数、搜索索引**一字未改
- [ ] 关联行数不变（软删除完全不碰 `entry_tag`）
- [ ] 重开软件 → 仍然是「列表里没有、日记上有」
- [ ] 在**别的一篇**上亲手敲同名标签 → 它回到列表里（复活）
- [ ] 老日记只是被重新保存/编辑一次 → 它**不会**自己冒回列表
- [ ] 老库升级（v2 → v3）→ 已有标签**一个不少**，篇数不变

## 功能 2：心情标记（P1 #9）

### 目标
每天给日记标一个心情，并在日历/统计里可视化。

### 数据
- `entry.mood INTEGER`（**已存在**，可空）
- **约定取值**：`1=很差 2=较差 3=一般 4=较好 5=很好`，`NULL=未标记`
- 日历格子上用对应的 emoji 或颜色点

### 关键设计（这里有个必须避开的陷阱）
**不能让 mood 变成"非空判定"的一部分。** 现有系统的核心规则是"`content_md` 去空白后非空 = 写过"。如果允许在一篇空日记上标心情，就会出现"有心情但没内容"的行，与"打开 ≠ 写过"直接冲突。

**做法**：把 `mood` 并入 `save_entry`，而不是单独开命令。
```
save_entry(date, title, content_md, mood: Option<i64>) -> Entry
```
- 后端规则：**`mood` 只在"这篇会被收录（有内容）"时才写入**；无内容时不落库（沿用现有的"空则不落库/删空行"逻辑）。
- 前端：`EditorPane.vue` 的心情条在内容为空时不显示（或置灰）；点某个心情 → 立即触发一次保存（把内容 + mood 一起写）。
- 这样：**永远不存在"有 mood 而无内容"的行**，日历标记规则完全不用改。

`commands.rs` 的 `save_entry` 加一个参数；`index.ts` 的 `saveEntry` 加一个参数。

### 前端表现
- `EditorPane.vue` 标题行右侧：5 个 emoji 按钮，当前心情高亮，再点一次取消（`null`）。
- `CalendarPanel.vue`：有心情的日子，在日期格子上显示对应 emoji（小号）。**注意：这只加"有心情"才显示的第三种标记，不要动已有的 written / today 逻辑。**
- `App.vue` 的统计区：暂时只显示，不做图表（图表归功能 6）。

### 验收标准
- [ ] 写内容后点 🥰 → 保存 → 重开这天的日记，心情仍是 🥰
- [ ] 把内容全部删空 → 心情与记录一起消失（不残留孤儿行）
- [ ] 日历上该天出现心情 emoji
- [ ] 心情不改变日历的"写过"标记逻辑（空内容的日期依然不标记）

> **实施中与本文档不同的四处 —— 都是有意为之，别照文档改回去：**
>
> 1. **验密码原语放在 `db.rs`，不放在 `crypto.rs`**。它要同时用 `CryptoMeta`（salt/参数）
>    和 rusqlite 连接，放 crypto 会把数据库依赖引进入加密模块。
>    公开两个函数：`open_verified_connection()`（开临时连接验密钥）、

> 2. **`change_password` 返回 `AppResult<Vec<String>>`（收尾警告列表），不是 `()`**。
>    `rekey` 之后的收尾（换提示语、同步免密钥匙文件）失败时，密码其实**已经换掉了** ——
>    用 `Err` 表达会让用户拿旧密码反复试。所以这两步只记警告，由界面如实显示。
>    命令层因此返回 `ChangePasswordResult { status, warnings }`（顺带回传最新 status）。
> 3. **"操作成功后立即备份"失败不算改密码失败**（同样只记日志 + 一条警告）；
>    另外**空库不备份**（一篇都没写），与自动备份同一口径，免得备份目录堆空库。
> 4. **没做"操作前再备份一份"这条建议**（见本节末"两条保险"第 1 条）。
>    理由：改密码前用户手里的库本来就是完好的，再复制一份价值有限，
>    而备份是整库复制、要占保留额度里的一个名额。留 TODO，等真有人喊再说。
>
> ⚠️ **实测结论（值得记住）**：`PRAGMA rekey` **在 WAL 模式下可用** ——
> 本项目所有连接都开 WAL，这条不确认清楚根本不敢写。
> 并且专门加了一条测试：改完密码后**把整个数据目录复制走**，仍能用新密码读全 ——
> 即 WAL 里不会残留"用旧密钥加密的页"（那会让库变成一半新钥匙一半旧钥匙，
> 属于不可逆丢数据）。

> 用户判断"这个简单"——判断正确。全库换钥匙由 SQLCipher 原生支持，不需要自己解密重写。
> 但有 **3 个必须处理的点**，漏了会出真事故。

### 原理
在**已解锁的连接**上执行：
```sql
PRAGMA rekey = "x'<新密钥的十六进制>'";
```
SQLCipher 会在库内部把整个文件用新密钥重新加密。日记内容一字不动，表结构不变，**不需要**"导出 → 重建 → 替换"那套。

### 后端要加的
`db.rs` 加 `Vault::change_password(old_pin, new_pin, new_hint, min_len)`：

```
① 校验新密码格式（复用 crypto::validate_pin）——不合格直接返回，什么都还没动
② 验证旧密码：用旧 PIN + 元信息里的 salt/参数派生出旧密钥，
   另开一个【临时连接】试开库（SELECT count(*) FROM sqlite_master）。
   打不开 → WrongPin，到此为止，库纹丝未动。
   ⚠️ 不要另写一套校验逻辑：把现有 open_with_key() 里的
      "PRAGMA key 是第一条语句 + 主动查询验证"抽成公共函数，两边共用
      （否则两处校验迟早漂移，违反项目"判定只实现一次"的原则）
③ 派生新密钥 → self.conn.pragma_update(None, "rekey", format!("x'{hex}'"))
④ 更新提示语（见下面第 1 点）
⑤ 清掉旧密钥/新密钥的内存（项目已有 zeroize 用法，照抄）
```

`commands.rs` 加 `change_password(state, old_pin, new_pin, new_hint)`，`lib.rs` 登记，`index.ts` 封装。

### 必须处理的 4 个点
1. **提示语（hint）必须一起改**。
   提示语存在 `lockout.json`（库外明文），内容形如"生日"。
   现在改完密码，旧提示还在，用户第 2 次输错会看到**照着旧密码写的提示** → 误导。
   而且 `record_success()` **只清失败次数、不清 hint**，所以要显式传新 hint（或显式清空）。
   → 命令签名带 `new_hint: Option<String>`，UI 上让用户重设（默认清空）。

2. **改密码也要计入锁定期**。
   验证旧密码时同样要：先 `check_not_locked()`（锁定中直接拒），失败要 `record_failure()`。
   否则"改密码"就成了一个**可以无限试旧密码的后门**（每次约 0.8 秒，6 位数字共 100 万种 ≈ 单线程跑 9 天），与项目"失败必须计数"的设计冲突。

3. **旧备份仍然用旧密码打开**。
   改密码只重新加密主库，`backups/` 里的历史文件是改之前复制出去的，**没被动过**。
   - 改密码**之前**的备份 → 用**旧密码**恢复
   - 改密码**之后**的备份 → 用**新密码**恢复

4. **免密开启时，必须同步更新 `auto_login.json`**（见功能 7）。
   这一条漏了，用户改完密码重启后免密就会失效（文件里还是旧钥匙，开不了库），
   而用户完全不知道为什么 —— 他刚做的事是"改密码"，看起来跟免密无关。
   做法：`rekey` 成功后，用**新密钥**重写 `data/auto_login.json` 的 `key_hex`
   （新密钥在该函数里本来就有，不必再派生一次）；免密未开启时跳过，不要顺手建文件。
   顺序必须是**先 rekey 成功、再写文件** —— 中途失败时文件仍是旧的，免密虽会失败，
   但用新密码能进，且功能 7 的回退逻辑会把免密关掉；反过来先写文件，就可能出现
   "文件是新钥匙、库还是旧钥匙"的死局。

### 复用同一个验证原语 —— ✅ 已抽出（2026-09-20）
功能 7 的 `derive_and_verify` 和本功能都需要"派生密钥 + 试开库验证"。
`db.rs` 里现在是这三个函数，**全应用只有这一份密钥校验**：

- `apply_key_and_verify(conn, key)`（私有）—— 真正干活的那几行：`PRAGMA key` 必须是
  连接后的第一条语句、用 `x'...'` 十六进制传、然后主动 `SELECT count(*) FROM sqlite_master` 验证。
- `open_verified_connection(db_path, key)` —— 开一个**一次性连接**并验证，不碰任何 pragma。
- `derive_and_verify(data_dir, pin) -> AppResult<[u8; KEY_LEN]>` —— 派生 + 验证 + 把密钥交回调用方。

三处入口都走它：改密码验旧密码、`Vault::unlock`（经 `open_with_key`）、功能 7 的免密校验。

⚠️ 调用方拿到密钥后**必须**用 `crypto::zeroize` 清掉（函数自己的失败路径已经清了）。
⚠️ `open_verified_connection` 会**先检查库文件是否存在**：`Connection::open` 对不存在的
路径会**创建**一个空文件，那就等于凭空造出一个明文空库，把用户的数据目录搞脏。

- **操作前自动备份一份**（复用现成的 `VACUUM INTO`），给用户留一个改前还原点。

### 为什么要改（原方案的两处硬伤）

| 硬伤 | 后果 |
|---|---|
| **钥匙写在 `crypto_meta.json` 里** | 这个文件是**打开库的必需文件**（salt + KDF 参数都在里面）。免密功能往它里面写，一旦写坏或被并发写坏，`CryptoMeta::load` 直接报"加密元信息损坏" → **连用密码都进不去**。一个可选功能不该有能力弄坏主路径。 |
| **免密之后就没有密码了** | 换电脑、恢复历史备份、想关掉免密重设密码 —— 这些场景都要靠密码，而它已经不存在了。用户会在"以为还能用密码"的时候发现进不去。 |

新方案把这两点同时解决，而且**成本更低**：切换免密不再需要 `PRAGMA rekey`（不重写整个库），只是写/删一个文件。

### 用户的原话与我的判断
> 用户说："自动用自己的密码去登录，直接明文记录密码。反正不要密码，安全性就是不需要的。"

安全判断**成立**：明文钥匙放在磁盘上，机密性就等于没有。这点不粉饰。

但要换掉"记什么"：

| 方案 | 做法 | 评价 |
|---|---|---|
| 用户原话 | 明文存**用户设的 PIN** | 用户会在别处复用这个密码（他以为自己在保护什么）；改密码时还要同时维护"文件里的明文密码"和"库的钥匙"两套东西 |
| **采用** | 明文存**库密钥本身**（32 字节的 hex） | 安全性**完全等价**（都是明文文件、都能直接开库），但语义干净：拿到钥匙就开库，不存在"密码被复用"这条额外泄漏路径。而且启动时**跳过 Argon2id**（省下那 0.8 秒） |

### 数据结构：独立文件 `auto_login.json`

**放库外，但绝不放进 `crypto_meta.json`。** 与 `lockout.json` 同目录、同写法（临时文件 + 原子改名）。

```jsonc
{
  "key_hex": "64 个 hex 字符 —— 库密钥本身",
  "created_at": 1758336000
}
```

- **文件存在 = 免密开启**。不设 `enabled` 字段：避免"文件在、字段却说关"这种自相矛盾的状态。
- 放库外是因为**启动时要能读到**（那时库还没解锁）。
- 位于 `data/auto_login.json`，被 `.gitignore` 的 `/data/` 覆盖；同时**像 `lockout.json` 那样单独列一行**，防止将来数据目录挪位时漏掉。

### 三个界面

**① 启动**：`boot()` 里 `getStatus()` → 若 `auto_login && !unlocked` → 调 `unlock_with_auto_key()` → 成功直接进主界面。**解锁页不出现**（`booting` 期间显示"正在启动…"，不会闪一下）。

为什么用前端调、而不是 `lib.rs` 的 setup 里自动开库：走前端能让**状态更新路径统一**（都经 `app_status`），且失败时能优雅回退到解锁页。setup 自动开库做不到这两点。

**② 点「锁定」**（已定：**A 方案 —— 像 Windows 没设密码那样，点一下就回来**）

免密开启时**不调 `lock_vault`**，改成一个纯前端的遮蔽态（`hidden = true`）：拉一层帘子，**点任意处 / 按任意键 / 点「继续」都能回来**，草稿不丢。

这跟"Windows 电脑可以不设密码"是同一个模型：系统不一定非要密码，`Win+L` 之后按一下键就回桌面。免密下"锁定"本来就锁不住任何人 —— 与其做一个点了就开的假锁定，不如把它做成一个诚实的遮蔽页，并在页面上写清它实际能防什么（只挡路过的人）。

⚠️ **手动锁定和自动锁定必须共用同一个 `doLock()`**（`App.vue` 里已经有这个函数，现在它只做一件事：`lockVault()`）。改成按 `auto_login` 分岔：

```
doLock()
  ├─ auto_login 开启 → hidden = true（纯前端拉帘子，不碰后端）
  └─ auto_login 关闭 → lockVault()（真锁，回解锁页）
```

两条路各写一份判断，迟早有一边漏掉 —— 而漏掉的后果就是"自动锁定把库真锁上、免密下又没密码可输"的死锁。

**③ 失败回退**：`unlock_with_auto_key` 失败时按原因分两类处理 ——

| 失败原因 | 处理 |
|---|---|
| 密钥对不上库（`WrongPin`） | **删掉 `auto_login.json`**（钥匙确实废了，留着只会每次启动都失败一次），回解锁页 + 提示"免密打开已失效，已自动关闭" |
| 文件内容坏了（JSON 残缺 / hex 长度不对） | **也删掉**。指令原文只点名了 `WrongPin`，但"留着只会每次启动都失败一次"这条理由对坏文件同样成立 —— 用户看到的现象一模一样（每次启动白失败一次），而他还不知道该去删哪个文件。判据落在**错误类型**上：`crypto` 类 → 删；`io` 类 → 留 |
| IO / 状态错误（库被占用、文件读不出） | **保留文件**，只报错回退。不能因为一次临时故障就把用户的设置清掉 |

实现落在 `commands::unlock_via_auto_login(data_dir)`（`pub`，集成测试直接驱动）：
读文件 → 取密钥 → `Vault::unlock_with_key` → 按上面的类型分岔。**成功路径也要 `record_success`**
（免密进得来就算一次成功解锁，清零失败计数），且必须**重新读一遍 `lockout.json` 再写回** ——
`save` 是整份覆盖写，用更早的副本写回会覆盖中间落盘的东西（功能 5 踩过同一个坑）。

### 必须处理的坑（顺序即优先级）

1. **免密下的自动锁定必须走"拉帘子"这条路，绝不能调 `lock_vault`**。
   旧的死锁是这么来的：自动锁定 → `lock_vault` → 回到解锁页 → 免密下没有密码可输 → 只能杀进程。
   遮蔽页把这颗雷拆了，但前提是**手动锁定与自动锁定共用同一个 `doLock()`**（见上面 ②）。
   ⚠️ 反过来同样要注意：**免密模式下的自动锁定是照常生效的**（它只是拉帘子，不会卡死）。
   不要再加 `if (auto_login) return` 去停用它 —— 那是旧方案里的规则，**已作废**。
   （这个时长本身可配，四档，见功能 11，默认 10 分钟。）

2. **开启免密必须先验证当前密码**。否则任何人趁你离开、屏幕还解锁着，点两下就能把它变成永久免密入口。→ `enable_auto_login(pin)` 收密码并验证，**并计入锁定期**（失败 `record_failure`、成功 `record_success`），与改密码同一套。

3. **关闭免密也验证一次密码**。理由不是防人，是**帮用户确认"我还记得密码"** —— 否则关掉免密、下次启动就进不去了。

4. **改密码时必须同步钥匙**。改了密码而 `auto_login.json` 还是旧密钥 → 下次启动免密失败。→ 见功能 5 的联动条目。

5. **`resolve_data_dir()` 的老问题在免密下更危险**。现有逻辑：从 exe 向上找 4 层 `data/`，**找不到就在 exe 旁静默新建一个空库**。免密下这会变成"双击一下就进了一个空白日记本"，用户以为日记全丢了，连密码提示都没有。→ 至少做一次显式确认。

   ⚠️ **本指令没有实施这一条。** 它超出指令范围，而且动的是"数据目录怎么解析"这条
   所有功能都踩在上面的路 —— 该单独做、单独测。记在这里只是**为了别忘了它**：
   免密把这个老问题的后果从"要我输密码"放大成了"我的日记不见了"。
6. **顶栏那条"按钮顺序：统计 → 设置 → 关于 → 锁定"已经过期了。**
   「关于」入口在 2026-09-20 被删掉（内容并进了设置页的【关于】分类），
   所以现状是 **统计 → 设置 → 锁定**，本指令无需再动。

### 安全语义（必须写在设置页上，不许粉饰）

- 钥匙明文躺在磁盘上，**免密开启后机密性等于没有**。它只挡"误开"和通用工具直读。
- **`data/` 目录整体被拷走 = 库能被直接打开**。这是有意的取舍（换来"恢复备份后仍能免密打开"）。
- ⚠️ **关掉免密 ≠ 钥匙消失**。删文件只是让程序不再读它，磁盘上可能仍有残留。**要真正作废，必须更换主密码** —— 那会把整个库用新密钥重新加密，旧钥匙从此解不开。设置页要提示这一点。
- ⚠️ `key_hex` 是明文，而项目用 git 管理：数据目录必须在 `.gitignore` 里（现有 `/data/` 已覆盖，另加一行显式声明）。做完跑一次 `git status --ignored`，确认待提交列表里没有 `auto_login.json` / `crypto_meta.json` / `*.db`。否则等于把钥匙和锁一起存档进 git 历史。

### 与功能 5（修改主密码）的联动 —— ✅ 功能 5 侧已落地（2026-09-20，提交 `83e3164`）
`change_password` 成功后，若免密开启 → 用**新密钥**重写 `auto_login.json`
（rekey 用的就是新密钥，函数里本来就有，不需要额外派生）。
顺序：**先 rekey 成功，再更新文件**。中途失败时文件还是旧的，用户用密码仍能进。

实现落在 `crypto::sync_auto_login_key(data_dir, key) -> AppResult<bool>`：

- **读原文、只改 `key_hex`、再写回**（不是重新序列化一个全新结构）——
  这样功能 7 以后往文件里加字段，不会被这里冲掉。
- **文件不存在时直接返回 `Ok(false)`，绝不顺手创建**。创建一个就等于替用户把免密打开了。
- 写入用"临时文件 + 原子改名"（`write_json_atomic`），与 `lockout.json` 同一手法。
- 失败**不算改密码失败**：那时密码已经换掉了，只记一条警告让界面显示
  （"免密钥匙文件未能同步…请关掉免密再重新打开一次"）。

> ⚠️ 功能 7 落地时注意：`sync_auto_login_key` 只负责**改已有的 `key_hex`**，
> "创建这个文件"还得功能 7 自己写（那是开启免密时的事，语义不同）。
> 而**路径**已经有现成的 `crypto::auto_login_path(data_dir)` —— 别再造一个拼字符串的地方。

### 为什么明确不做 G（按字面理解的那个方案）

"点击日历上的日期 → 改这个日期"听上去最贴字面，但它是**危险的错方案**：

- 一天一篇由数据库 `UNIQUE(entry_date)` 保证。把某天挪到另一天意味着**两个日期同时要改**：
  源日期要删空、目标日期可能已有内容（**会被覆盖，这是丢数据**）。
- 还要额外处理：锁定日不能挪、双索引要重建、`mood` 跟谁走。
- 而且它**根本解决不了"跨月导航慢"**这个真实痛点。

### 采用的方案（A + D）

#### 交互

点标题 `2026年9月` → 标题下方浮出面板：

```
‹   2026 年   ›          ← 年份，左右箭头步长 1 年
1月  2月  3月
4月  5月  6月
7月  8月  9月            ← 当前月高亮
10月 11月 12月
─────────────────
今天   第一篇   最近一篇
```

- 点某个月 → 跳到该月并关闭浮层
- 点浮层外部 / 按 `Esc` → 关闭
- 底部三个入口：`今天`（跳到今天并选中）、`第一篇`（最早写过的日子）、`最近一篇`（最近写过的日子）

#### 改哪些文件

| 文件 | 改什么 |
|---|---|
| `app/src/components/CalendarPanel.vue` | 全部新逻辑（浮层、年月格、三个入口） |
| `app/src/App.vue` | 给 `CalendarPanel` 传两个新 prop：`:first-date` / `:last-date` |

**不需要改后端任何文件，不需要新增命令。**

#### 数据从哪来（不用新命令）

`stats` 命令返回的 `Stats` **已经有** `first_date` / `last_date`（`db.rs` 的 `stats()`），
且它们是按 `has_content_sql()` 过滤的 —— 即"真正写过"的日期，不会把打开过的空日期算进来。
`App.vue` 已经在调 `getStats()` 并存了 `stats`，所以只需往下传两个字符串。

#### 关键设计与坑（照这个做，别自己发挥）

1. **不产生任何数据、不写库。** 这只是"换个角度看日历"。碰到 `save_entry` / `has_content` /
   `written_dates` / `written_moods` 的任何逻辑，就说明跑偏了。
2. **只换月份，不改选中的日期。** 现在点 `‹` `›` 也只是 `month.value` 变、`selected` 不变。
   浮层跳月必须保持同一行为 —— 否则用户只是想看看 2024 年写了什么，编辑区却被切走了。
   **例外只有底部三个入口**：它们**要**同时改 `selected`（意图就是"去那天"）。
3. **切月后的标记重载由 `watch(month, load)` 自动完成**，**不要手动再调一次 `load()`**，
   否则每次切月发两次 IPC。
4. **浮层定位需要 `position: relative`**：`.calendar` / `.head` 目前都没有定位上下文，
   直接 `position: absolute` 会相对整个窗口定位、位置乱飞。`z-index` 建议 20，要盖住日期格。
5. **监听器必须清理**：`Esc` 与"点外部关闭"要在 `onUnmounted` 里 `removeEventListener`，
   否则组件反复挂载会累积监听器。
6. **"点外部关闭"不能用 `click` 判断**：会和打开浮层的那次点击冲突（浮层刚开就被自己关掉）。
   用 `pointerdown` 并判断事件目标是否在浮层/标题内，或加 `nextTick`。
7. **年份要 clamp**：建议范围 `firstDate 的年 −1` ~ `当前年 +1`，没有任何日记时只显示当前年。
   不允许无限翻到 1900 / 2100 年。
8. **不要改动日期格上已有的三种视觉**：`written` 的圆点、`today` 的高亮框、`mood` 的小表情。
   也不要改任何"写过"的判定。
9. **版本归属**：本条不在 P1 六项内，属于 P0 阶段的即时 UI 调整 → 落地时走 `1.x` 记账
   （预计占 1.6，会把原定的"文档补更新"顺延）。

| 做法 | 以后加一项的成本 | 代价 |
|---|---|---|
| **通用读 `get_settings()` + 专用写**（采用） | 加一个字段（0 条新读命令） | 写入各自有校验，安全边界清楚 |
| 全部走通用读写 `get/set(key, value)` | 0 后端改动 | 前端能写任意 key，**必须加白名单**，否则成了"能改任意设置"的口子 |
| 每项都专用命令 | 每次改四处 | 最啰嗦 |

1. `AppSettings` 结构加一个字段（**通用读**，就这一处）
2. 加一条专用写命令（`db.rs` → `commands.rs` → `lib.rs` → `api/index.ts` 四处联动）
3. 设置页加一行

`get_settings()` 读的是 `app_setting` 表，它在**加密库里** → **未解锁时读不到**。
而启动时恰恰需要知道"免密是否开启"（那是在解锁之前）。

所以这个信息必须由 `app_status` 提供，读**库外的 `auto_login.json`**。
不要把这两条路径混成一条。

### 坑
1. **只搬 UI，不重构后端**。备份三项的命令一个字都不用改。
2. **别把「关于」的只读信息搬进设置** —— 那会让设置页变成杂物间。
3. **设置组件不要自己拉状态**，一律从 `App.vue` 通过 props 传。自己再调一次 `getStatus()` 会多一次 IPC，而且两份状态不同步。
4. **左栏不能跟着右栏一起滚**，否则切分类时看不到导航。
5. 不引入组件库、不新增颜色变量 —— 复用现有 CSS 变量，主题跟随系统。

## 功能 11（新增）：自动锁定时长（1 / 5 / 10 分钟 / 永不）

### 要解决的问题
"离开多久自动锁"现在是**写死的 15 分钟**（`App.vue` 里的 `AUTO_LOCK_MS`）。
不同人对"多久算离开"的容忍度差很远：有人希望切出去一会儿就锁上；有人写日记时要频繁查资料，
每次回来都被锁很烦。做成四档设置项，让用户自己挑 —— 和 Windows 里能设"多久后锁屏"是同一件事。

### 档位（已定，就这四档）

| 档位 | 秒 | 备注 |
|---|---|---|
| 1 分钟 | 60 | |
| 5 分钟 | 300 | |
| 10 分钟 | 600 | **默认** |
| 永不 | 0 | 不自动锁；只有手动点「锁定」才锁 |

**默认值是一次行为变更**：现有行为是硬编码 15 分钟，而四档里没有 15 → 取最接近的 **10 分钟**。
老库（`app_setting` 里没有这个 key）走同一默认值。**要记进生产日志。**

### 计时起点：与 Windows 的差别，要如实说
本项目是**按"窗口失去焦点"计时、重新聚焦就取消** —— 这是 `onBlur` / `onFocus` 里现成的行为，改动最小。
Windows 的自动锁定是按**系统空闲时间**算的（跟"人在不在电脑前"挂钩），那要调系统 API，本项目不做。

### 免密打开开启时照常生效（这条推翻了原方案）
原方案里有一条硬规则："免密开启时必须停用自动锁定"。**现在不需要了** ——
因为锁上之后进的是遮蔽页（功能 7），点一下就回来，不会卡死。
所以免密模式下自动锁定照常跑，只是"锁上"这个动作变成了拉帘子。

前提仍然是：手动锁定与自动锁定**共用同一个 `doLock()`**（见功能 7 的坑 #1）。

### 后端改动

| 文件 | 改动 |
|---|---|
| `db.rs` | 新增 `AppSettings` 结构 + `get_settings()`（读 `app_setting`；缺失 / 解析失败 / 值不在白名单 → 一律回落 600）；新增 `set_auto_lock_secs(secs)`（**只接受 0 / 60 / 300 / 600**，其他值返回 validation 错误） |
| `commands.rs` | 新增 `get_settings()`、`set_auto_lock_secs(secs)`，**两条都走 `with_vault`**（读写的是加密库） |
| `lib.rs` | 登记两条新命令 |
| `api/index.ts` | 加 `AppSettings` 类型 + `getSettings()` / `setAutoLockSecs()` 两条封装 |
| `SettingsPanel.vue` | 【安全】分组加一行（壳在功能 10 里已建好） |
| `App.vue` | `AUTO_LOCK_MS` 常量换成来自设置的秒数；`0` = 永不（不注册定时器） |

### 读路径为什么不能走 `app_status`
`app_setting` 表在**加密库里**，未解锁时读不到；而 `app_status` 恰恰是"未解锁也要能调"的那类命令
（`max_attempts` / `lockout_secs` 都来自库外的常量与 `lockout.json`）。
所以硬塞进 `app_status` 只会得到默认值或 null，**反而误导前端**。

正确做法：读走 **`get_settings()`（需解锁）**，前端**解锁之后**才拿它挂定时器 ——
未解锁时本来也不需要计时。

这也正是功能 10 里承诺的「**通用读 + 专用写**」的第一位使用者：
以后再加设置项，只要 `AppSettings` 加个字段 + 一条专用写命令 + 设置页加一行。

### 坑
1. **改完设置必须立刻重挂定时器**。设成「永不」时如果只把变量改了、旧 timer 还在走，到点照样会锁。
   → 设置变更后先 `clearTimeout`，再按新值决定挂不挂。
2. **上锁 / 进入未解锁态时要清掉 timer**，否则解锁后可能被上一轮遗留的定时器突袭。
3. **持久化失败要如实报错并把 UI 回滚成原值**，不要本地改了 `ref` 就当成功 ——
   否则下次启动值又变回去，用户会以为设置没保存。
4. **不要顺手重构** `onBlur` / `onFocus` / `humanInterval` 这些周边逻辑，本次只动这一个值。
5. 设置项的 key 用 `auto_lock_secs`（下划线风格，与现有 `app_setting` 用法一致）。

### 难度
★（低）。后端只有一对读写 + 一条校验；前端只是把常量换成状态值。
它是"加一项设置"的最小完整示范，**最适合排在设置页骨架之后马上做**。

### 验收标准
- [ ] 设置页【安全】出现「自动锁定时长」，四项：1 分钟 / 5 分钟 / 10 分钟 / 永不，
      文案一视同仁（无括号说明）
- [ ] 选 1 分钟 → 失焦超过 1 分钟 → 锁定（有密码模式回解锁页；免密模式出遮蔽页）
- [ ] 选 10 分钟 → 失焦 2 分钟不锁，超过 10 分钟才锁
- [ ] 选「永不」→ 失焦放置很久也不锁；手动点「锁定」仍然正常
- [ ] 改完**不用重启**立刻生效
- [ ] 从「1 分钟」改成「永不」后立刻不再自动锁（旧 timer 已被清掉）
- [ ] 重启后设置仍是上次选的值
- [ ] 老库（从未设过此项）→ 默认 10 分钟
- [ ] 手动往库里写一个非法值（如 123）→ 回落默认，不崩

## 功能 14（新增）：日记「离开时自动锁定」开关

> ## ✅ 已实施（2026-09-22 · 提交 `2fa8fd1` · 版本 **`2.5`**）
>
> 一条未改地落地：**这个行为原来就存在（写死在 `EditorPane.load()` 首句），本功能把它变成开关**。
> **只动设置页那一行 ＋ 编辑器读设置那一处，没有改动任何别的语义。**
>
> 拍板要点：设置页【安全】里**紧挨着"自动锁定时长"**；**默认开**（＝与改动前逐项一致）；
> key `auto_lock_entries`；**关掉 ≠ 解锁已锁的日记**；🔒 手动按钮不受影响。
>
> 三个最容易写反的地方（下面「坑」那节都点过名，实施时逐条守住了）：
> ① 读设置**只有精确 `"false"` 才算关**，其余一律按开 —— 与 `auto_backup_enabled()` 的口径
> **故意相反**，因为**锁定读错方向是静默地失去保护**；
> ② 前端 `autoLockEntries` **初值 `true`**、编辑器判 `!== false`（`undefined` 按"锁"）；
> ③ **"先保存、后锁定"的次序一个字没动**。
>
> 验收：`cargo test -p app` **128 项全过**；CDP 连真实 DOM 验 7 项（含回读落库值、
> "关掉后切走再切回不再自动锁"）。详见 `生产日志.md` 3.3 节「指令 14」。

> 📌 **编号说明**：12 / 13 曾分配给已作废的"窗口模式 / 记住窗口几何"
> （见 0.3 节的"明确不做"），**编号不复用**，所以新功能从 **14** 续。
> 它对应的指令包是 `Diary-给AI的逐条指令-P1.md` 的 **【指令 14】**，
> 标签增强则是 **指令 5 的增强包**。

### 要解决的问题

用户原话：
> "增加一个文章锁定是否自动开启，因为有的人喜欢锁定防止误删，有的人不喜欢一直锁定。"

⚠️ **先把一件事说清楚：这个行为现在就已经存在，而且是写死的，不是"从零新增"。**

`EditorPane.vue` 的 `load()` 第一句就是：

```ts
// 先把所有日记锁上，再读要打开的这一篇。
// 于是"切换日期"和"重新打开软件"都会让上一篇自动回到锁定状态。
await lockAllEntries();
```

所以现在**切到别的日子、或者重开软件，写过的日记就一定会变成锁定的**
（"锁定"= 只读：`save_entry` 拒绝改、`delete_entry` 拒绝删、打标签也拒绝）。
用户说的"不喜欢一直锁定"，就是它 —— 想回头补一句，得先点解锁。

**所以本功能 = 把这一句写死的行为变成开关。**

### 形态（已定）

设置页【安全】分组加一行（紧挨着"自动锁定时长"）：

- **开** = 与今天逐项一致
- **关** = 切回某天仍是**可编辑**状态，不用反复解锁；想锁时点 🔒 手动锁

### ⚠️ 最容易搞错的地方：它和功能 11 不是一回事

| | 功能 11「自动锁定时长」 | 本功能「离开日记时自动锁定」 |
|---|---|---|
| 锁的是**什么** | **整个应用** —— 回到解锁页 / 遮蔽页 | **单篇日记** —— 那天的正文变成只读 |
| 由什么触发 | **窗口失去焦点**超过 N 分钟 | **离开这一天**（切日期 / 重开软件） |
| 解决什么 | 别人碰你电脑时看不到内容 | 防止自己手滑改掉、删掉写好的日记 |
| 设置 key | `auto_lock_secs` | `auto_lock_entries`（**别和上面的搞混**） |

两个"自动锁定"**同名不同义**，所以 key、文案、在分组里的位置都必须能一眼分开。
设置页这两行要挨着放，避免用户以为是同一个开关。

### 坑（顺序即优先级）

1. ⚠️ **"先保存、后锁定"的次序一个字都不能动。**
   `EditorPane.vue` 里那段 `watch(props.date)` 上留着血泪注释：先锁再存 →
   这次保存会被刚上的锁拒绝，用户最后敲的几个字**静默消失**。
   本功能只是让"锁定"这一步**可能不执行**，**绝不改变"保存永远在锁定之前"这个次序**。
2. ⚠️ **设置还没读到时，按"开"处理（＝默认值）。**
   `load()` 是首屏就调用的，而 `get_settings()` 要等解锁之后。
   要是把"还没拿到设置"当成 `false`，就会出现"重开软件后日记居然还是未锁的"
   —— 与默认值刚好相反，而且是**静默**的，极难查。
   → 前端把 `autoLockEntries` 的**初值直接设成 `true`**，读到设置再覆盖。
3. **手动锁定按钮（🔒）不受这个开关影响**，永远可用。开关管的是"自动"那一半。
4. **`lockAllEntries()` 锁的是全库所有未锁日记，不只是上一篇。** 保持原样 ——
   别"顺手优化"成"只锁上一篇"，那会让别的日子漏锁，而**漏锁是静默的**
   （用户不会发现某天的日记没被锁上，直到误删）。
5. **关掉开关 ≠ 解锁已锁的日记。** 它只影响"以后要不要自动锁"。
   已经锁上的那篇仍要点 🔒 解锁 —— 否则就成了"改个设置把所有保护一次性抹掉"。
6. **别顺手重构** `lockAllEntries` / `set_entry_locked` / `is_locked` 的语义，本次只加一个开关。
7. 设置项的 key 用 `auto_lock_entries`（下划线风格，与 `auto_lock_secs` 一致）。

### 要解决的问题

用户原话：
> "我想要的方便就是一只手可以快速解锁，我都要摁ctrl键了还不如手动去点击解锁，
> 就左键三下解锁，平常也不会一直点击左键。"

背景：单篇日记的锁定（右上角 `🔒 已锁定`）是**防误改**用的，所以"打开旧日记想接着写"
几乎必然要先解锁一次。而解锁目前只有一条路 —— 把鼠标移到编辑器右上角去点那个按钮。
用户的诉求是**手不离开正文**就能解锁，省掉"看一眼 → 想补一句"之间的一次鼠标位移。

⚠️ 注意这里锁的是**单篇日记**，**不是**"整个库的锁"（顶栏「锁定」/ 免密遮蔽页），
也**不是**功能 11 的自动锁定时长。三层"锁"同词不同物，见功能 14 那一节的对照表。

### 形态（已定）

设置页【安全】分组加一行（紧挨着"离开日记时自动锁定"）：

| 行 | 控件 | 默认 |
|---|---|---|
| **三击左键快速解锁** | 开关 | **开** |
| └ 说明 | "日记锁定时，在正文里连续点三下左键即可解锁，手不用移到右上角。关掉后只能用 🔒 按钮解锁。" | |

- **手势**：**只在日记处于锁定态**时，在**正文输入框**上左键连点 3 下（相邻两下间隔 ≤ 500ms）→ 解锁这一篇
- **方向是单向的**：只做"解锁"。锁定仍点右上角那个按钮
  （用户 2026-09-21 明确：不需要"双击右键锁定"那条手势）
- **不碰右键**：因为不做右键手势，`contextmenu` 一行都不用动 —— **正文的右键菜单原样保留**
  （复制 / 粘贴照旧。这是砍掉右键手势最主要的"意外收获"）
- 手动 `🔒 / 🔓` 按钮**不受影响**，永远是主入口、也是唯一能"锁定"的入口
- **默认值必须是"开"** —— 老库（没有这个 key）走同一默认值

### ⚠️ 为什么是"三击"而不是别的（频率论证，别再翻案）

正文输入框里鼠标的三种点击各有原生用途：

| 动作 | 原生用途 | 频率 |
|---|---|---|
| 单击左键 | 放光标 | 最高 |
| 双击左键 | 选中一个词 | 中 |
| **三击左键** | **选中一整段** | **最低** |

三击是**误触率最低**的那一档，正好拿来当手势 —— 用户"平常也不会一直点击左键"这句判断是对的。
（另外两条曾被考虑、已否掉：`Ctrl+L` 要**两只手**，与"单手"这个**唯一诉求**相抵，等于"不如直接点按钮"；
"双击右键锁定"会抢 WebView2 的默认右键菜单，得不偿失 —— 且用户也已撤回。）

### 关键设计（照这个做，别自己发挥）

1. **只在 `locked === true` 时听。** 未锁定状态下三击必须保持浏览器原生的"选中一整段"——
   这是本功能**边界最小**的关键：解锁态的行为一个字都不变。
2. **用 `mousedown`，不用 `click`。** 且在第 3 次 `mousedown` 上 `preventDefault()` ——
   否则 `readonly` 的 textarea 会顺势"选中一整段"，解锁瞬间满屏高亮。
3. **阈值用"时间窗口"，不用"计数器 % 3"。** 记住上一次点击的时刻，间隔 > 500ms 就把计数清零；
   否则"慢慢悠悠点三下"也会触发。
4. **只挂在正文 `textarea` 上，绝不挂 `.editor`。** 挂整块的话，在「🔒 已锁定」按钮 /
   心情按钮 / 标签 `×` 上三击会**连带触发**，与按钮自身的点击打架。
5. **复用 `toggleLock()`**，不要另写一条 `setEntryLocked` 路径 —— 它已经处理了
   "先保存、后锁定"的次序，并且用**后端返回值**回填 `locked`（界面状态以库为准）。
6. **触发后给一条提示**（"已解锁"）—— 复用第 2 项加好的 `notice` emit，别新造提示通道。
7. **关掉开关 = 真移除监听**，不是"监听了再 `return`"。

### 坑（顺序即优先级）

1. ⚠️ **解锁态三击必须保持"选中一整段"**（见关键设计 1）—— 这是最容易"改坏既有行为"的点。
2. ⚠️ **第 3 下要 `preventDefault`**，否则满屏选中（见关键设计 2）。
3. ⚠️ **别碰 `contextmenu`。** 右键手势已撤回，本功能与右键**完全无关**；

5. **手动按钮永远是主入口。** 别把"三击"做成唯一解锁方式 —— 手势坏了也得有按钮能解。
6. **别顺手改 `toggleLock` / `set_entry_locked` / `lockAllEntries` 的语义**，本次只加一个手势。

## 功能 16（新增）：日历年月面板 —— 年份可直接输入

> ## ✅ 已实施（2026-09-22 · 提交 `1414e04` · 版本 **`2.4`** · 配套指令 16）
>
> 用户给截图圈定面板里 `2029 年` 那一处，要能直接输入想去的年份，并明确
> **"先不用实行，告诉我其中还需要确认的细节"** ⇒ 先出待确认清单（**这套流程本身就是设计的一部分**），
> 他逐条拍板后才动手。**只动 `CalendarPanel.vue` 一个文件**，后端零改动。
> 详见 `生产日志.md` 3.3 节「指令 16」。

### 要解决的问题

年月面板里的年份只能靠 `‹ ›` 一格一格挪。从 2029 回到 1998 要按 **31 下**、
去 2099 要按 **70 下** —— 想"去某一年看看"这件事，比它该有的样子贵得多。

范围已经在 2026-09-22 放宽到 `1949 ~ 2099`（原先是跟着 `firstDate` / 今年算的，
日记本很新时等于没余量）。范围放开之后，"一次挪一年"就成了唯一还没解决的瓶颈。

### 设计

**做成什么样**：面板里 `‹ 2026 年 ›` 中间那个年份，**点一下变成输入框**，
打进年份按回车，面板年份就跳过去。

**为什么是"点一下才变"而不是常显一个输入框**：常显更省一步，但用户当场否掉了 ——
"太丑了"。面板里那一行要跟两侧的箭头保持克制，常驻一个带边框的输入框会把它压散。
所以默认仍是文字，`cursor: text` + 悬停给个淡淡的底，暗示"这儿能点进去打字"。

**五个必须定的分叉点**（这就是"先出清单再动手"的价值 —— 这些用户不会主动说，但改法完全不同）：

| 分叉点 | 定案 | 为什么 |
|---|---|---|
| 输完走哪 | **只换面板年份**（不选月份、不关面板） | 与 `‹ ›` 同口径。用户可能只是想"看看那年"，替他选月等于替他做决定 |
| 输错了怎么办 | **夹到边界**（1800 → 1949、3000 → 2099） | 有反馈、又不会把输入扔掉。夹不了的空输入退回原值 |
| 什么算"打完" | **只有回车** | 打满 4 位自动生效更快，但打错一位就没法改（第 4 位一落就跳走） |
| Esc 冲突 | **一律关面板** | 与面板外一致，不引入"第一次 Esc 只撤销"的第二套语义 |
| 草稿怎么处置 | 失焦 / 点箭头 / 点月份 **一律放弃草稿** | 不这么做的话，"打一半又去点箭头"会先提交再步进、一下跳两年 |

**一个刻意的克制**：输入过程中**不校验、不 clamp、不弹回**。打 `1800` 要经过 `1`、`18`、`180`，
每一步都"不在范围内" —— 实时夹的话第一个字符就被弹掉，根本打不进去。

**中文输入法**：回车提交前必须看 `ev.isComposing`（中文输入法里 Enter 是"上屏候选词"）。
这是本项目唯一一处 IME 相关代码。另外全角数字（`１９９８`）会先折成半角再过滤。

### 涉及文件

| 文件 | 改动 |
|---|---|
| `app/src/components/CalendarPanel.vue` | 全部逻辑（两态切换、输入过滤、提交校验、收尾清理）。**只有这一个文件** |

后端零改动、`App.vue` 不用动、不写库、不新增命令。

### 验收标准

（与《逐条指令》里「指令 16」的验收清单相同，逐条列在那里。）

### 顺带留下的一条经验

**验界面交互，别靠合成鼠标点击**。这轮先用 `SetCursorPos` ＋ `mouse_event` 点"日历标题"，
坐标忘了按 DPI 缩放换算（144 dpi ⇒ ×1.5）**点空了，而截屏上"看着像点开了"** ——
差点误判成"功能正常"。正确姿势：启动时带
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<port>`，
用 CDP 的 `Runtime.evaluate` 直接在页面里点元素、读回 DOM 文本。
**夹边界、输入法不提交、失焦弃稿这类逻辑，只有这条路验得了**，而且不吃窗口位置和 DPI。
