> ⭐ **一句话**：日记这个项目里**所有「以后还想翻」的东西，都住在这一层**。
> 代码之外的全部留档（进度、决策、指令、验收证据）都收在这儿，别处不再有副本。

> 原先是散的：生产日志在仓库根、其余文档在桌面另一个文件夹
> —— 于 2026-09-29 按用户要求**全部搬进来、原位置清空**。

## 一、里面有什么

| 文件 | 是什么 | 什么时候看它 | 谁在改 |

## 二、三条不能破的规矩

1. **「做完了」要标三处**（只标一处等于没标）：
   `Diary-给AI的逐条指令-P2.md` 的 ✅ 块 → `Diary-P2功能列表.md` 的挑活表 → `生产日志.md`。
   ⚠️ **挑活表最容易漏**。
2. **`生产日志.md` 自己内部有 5 个地方要动**（不是改一处就完）：
   第 6 行「最后更新 / 当前版本」→ 五、当前状态标题 → 测试段实测数 → 产物表 ＋ 变更记录 ＋ 坑表 → 八、下一步。
   ⚠️ **第 6 行顶部摘要 ＋ 总表那行「下一件」最容易漏**（`3.11` 那次两条都漏、`3.12` 才补上）。
3. **改长行表格（产物表 / 变更记录 / 挑活表）必须用 Python 脚本改**：
   直接拿 `Read` 的输出当 `old_string` 去 `Edit` **必然失败** ——
   `Read` 只回每行前 2000 字符、行尾是 `[truncated]`。
   脚本里每条锚点都写 `assert` 命中**恰好一次**，写完查 `U+FFFD`（乱码）为 0。

## 三、版本号怎么走

- P2 段 ＝ **`3.x`**，**做一件 +1**。
- ⚠️ 历史包袱：`2.8` / `2.9` / `2.10` 是 P2 的头三件（**号不回改**）。
- **修 bug 的补丁不占条数**（例如 `3.4` / `3.10`）。
- 三处版本号要同时改：`app/package.json`（可两段 `"3.14"`）／
  `app/src-tauri/tauri.conf.json`（**必须三段** `3.14.0`）／`app/src-tauri/Cargo.toml`（**必须三段**）。
  界面【关于】显示的是 `package.json` 那个。
- **体积数字读不出改了什么，只认 `sha256`**（已多次出现「与上一版一字不差但内容变了」）。
- ⚠️ **验收对象必须是发布件本身**（`发布\日记.exe`）：`tauri build` 的产物与裸
  `cargo build` 的产物**字节数可能不同** ⇒ 验过的那个必须等于用户拿到的那个。

## 四、改完一件之后的标准流程

```
改代码 → 跑全量测试 → 构建 → 刷发布件 → 界面验证 → 冒烟
      → 记账（上面那三份文档）→ git commit → 记生产日志 → 刷 发布\日记.exe
```

- 全量测试：**`cargo test -p app -j 1 -- --test-threads=1`**
  ⛔ **绝不能加 `--release`**（`[profile.release] panic = "abort"` 与测试 harness 需要的
  `unwind` 冲突 ⇒ 172 个错、一条测试都没跑起来）；`-j 1` 是必须的
  （`--release` 下 cargo 会并行构建同名目标、自己抢自己）。
- 判成败**只认 `test result:` 行**（单测红会整轮中止，集成测试根本不跑）。
- 发小版本：`publish-exe.ps1 -SkipBundle`
  ⚠️ **前端有改动时不能加 `-SkipBuild`**（它会把 `tauri build` 连 `pnpm build` 一起跳过，发布件根本不更新）。
- **安装程序等 P2 全完再出**。
