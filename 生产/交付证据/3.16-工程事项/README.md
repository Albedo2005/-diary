## 1. 老数据不丢 —— 拿**真·旧格式库文件**跑升级

**缺口**：`db.rs` 里那两条迁移单测是"从当前库删列退回旧版"**模拟**的老库，
从来**没拿一份真正的旧格式文件开过** —— 而"模拟出来的老库"和"当年真写出来的老库"
是两回事（真库可能带着模拟时想不到的历史形态）。

**做法**：新增 `app/src-tauri/tests/migrate_real_old_vault.rs`（`#[ignore]`，需用户本机真数据）。
它用用户自己真实库里升级前留下的快照 —— `data\diary.pre-v1.db`（schema v1，2026-09-11）
和 `data\diary.pre-v2.db`（schema v2，2026-09-21）—— 跑一遍完整升级，逐篇逐字比对。

两条红线（写在测试文件头部，也在代码里）：
1. **只在临时目录的副本上操作**，源文件一个字节都不碰；
2. **绝不打印密钥内容**，只报长度。

| 真快照 | 升级前 | 升级后 | 结果 |
|---|---|---|---|
| `diary.pre-v1.db` | 10 篇 / 0 条标签关联 | schema **v1 → v3**，10 篇 / 0 条 | ✅ 正文共 **1116 字符逐字未变** |
| `diary.pre-v2.db` | 18 篇 / 9 条标签关联 | schema **v2 → v3**，18 篇 / 9 条 | ✅ 正文共 **2017 字符逐字未变** |

比对的口径：`entry_date / title / content_md / word_count / mood / created_at / updated_at`
七个字段**逐条相等**，外加标签关联**整组相等**（不是"数量对得上"，是**内容也一模一样**）。
另外断言升级前快照 `diary.pre-vN.db` 必须留下 —— 那是出事之后唯一的退路。

⚠️ 刻意**不比 `locked`**：那一列是 v1→v2 才加的，老库里根本没有，
拿它做前后比对必然对不上 —— 而这里要回答的是"迁移有没有动数据"。

**复跑**：
```bash
DSH_REAL_VAULT_DB="<老库文件>" \
DSH_REAL_VAULT_KEYFILE="<含 key_hex 的 auto_login.json>" \
DSH_REAL_VAULT_LABEL=v1 \
cargo test -p app -j 1 --test migrate_real_old_vault -- --ignored --nocapture
```

## 2. 崩溃恢复 —— 写到一半强杀，重开后数据完整

**缺口**：写入本来就建在 `unchecked_transaction` ＋ SQLite WAL 上，底子是好的，
**但一个"强杀"测试都没有** —— 也就是说，"它扛得住"这件事从来没有被验过。

新增 `app/src-tauri/tests/crash_recovery.rs`，两条路子互补：

### 2a. 真强杀（`kill_mid_write_then_reopen_is_consistent`）

起一个子进程不停往同一篇写 300 KB 正文，父进程**确认它已经提交了 ≥3 轮**之后
用 `Child::kill()` 打死（Windows 上是 `TerminateProcess`，进程没有任何收尾机会），再重开。

> ⚠️ "确认提交了 ≥3 轮"这一步不能省：靠 sleep 猜的话，机器一快一慢就可能
> **杀在一个字都还没写进去的时候**，于是"重开后数据完好"变成一句**什么都没验的空话**。
> 这里用子进程的 stdout 当信号 —— 它每写完一轮就打印一行。

实测：`强杀后重开：拿到完整第 2 轮，300008 字符`，断言四项全过
（SQLite `integrity_check` = ok ／ 索引体检健康 ／ 没被碰过的那一篇一字未变 ／
被反复重写的那一篇读到的是**完整的一轮**）。
"完整"的判据是**正文长度正好 300008 且前 8 位是一个合法轮次号** ——
半条、截断、串页都会当场露馅。

### 2b. 确定性复现"事务开着时进程没了"（`torn_wal_recovers_to_last_commit`）

2a 杀在哪一瞬是**概率性**的（多半落在两次提交**之间**），盖不住
"事务开着的时候整个进程没了"那一档。这条专门补它：开事务 → 写一大段 → **不提交**，
趁事务还开着把整个数据目录抄走（⛔ 不抄 `-shm`，崩溃时它本来就是废的），
那份拷贝就是"进程正好死在这一刻"留在盘上的样子。

实测：`WAL 193672 → 403792 字节`（**未提交的帧确实落到盘上了**），
重开后已提交的那篇完好、未提交的那条按预期消失。

> ⭐ 这条测试的**关键**是一句前置断言：`wal_after > wal_before`。
> 没有它，如果 SQLite 把未提交的帧全留在内存里（**实测默认就是这样**），
> 那份"崩溃现场"里根本没有未提交帧，而测试**照样会绿** —— 绿得毫无意义。
> 为了让帧真的落盘，测试里把该连接的页缓存压到 128 KB（`PRAGMA cache_size = -128`）
> 逼它溢出。**这条经验写进坑表了。**

## 3. 数据规模 —— 列表 / 搜索 / 统计到底卡不卡

新增 `app/src-tauri/tests/scale.rs`（`#[ignore]`，规模可用 `DSH_SCALE_N` 覆盖，默认 **2 万**）。

> ⚠️ **先说清"多少篇才算多"**：表上是 `UNIQUE(entry_date)` —— **一天最多一篇**。
> 所以 N 篇就是 N 个不同的日子：**2 万篇 ≈ 59 年、10 万篇 ≈ 297 年**，
> 天天不断。**"10 万篇"是物理天花板，不是用户会遇到的场景** ——
> 这就是默认规模定在 2 万的原因。

### 2 万篇（约 59 年）实测

| 操作 | 耗时 | 评级 |
|---|---|---|
| 灌数据（一次性） | 144ms | — |
| 重建索引（一次性） | 2119ms | — |
| 列表：某一个月的日记（28 条） | **162ms** | 轻快 |
| 搜索「公园」 | **44.5ms** | 无感 |
| **统计页** | **1477ms** | **卡** |
| 日历：一整年 | **91ms** | 无感 |
| 筛选最新 200 条 | **457ms** | 可察觉 |
| 索引体检 | **572ms** | 可察觉 |

（另有 `3,650 篇 ≈ 10 年` 那一组：列表 168ms ／ 搜索 3.8ms ／ **统计 489ms** ／
日历 74ms ／ 筛选 243ms ／ 体检 239ms —— 全部在 500ms 以内。）

### ⚠️ 找到的真实瓶颈（**未修，已报给用户**）

**统计页在 2 万篇下要 1.5 秒**：`stats()` 连着跑了 **5 条全表查询**
（总篇数 / 总字数 / 全部日期 / 心情分布 / 每月字数），
**每一条的 `WHERE` 里都挂着 `has_content_sql()`** ——
那是个"逐行剥离 HTML 标签"的长表达式（一串嵌套 `REPLACE` / `INSTR`，外加一个
附件 `EXISTS` 子查询）。于是 5 × 2 万行都要把那串表达式算一遍。

`list_month` 的执行计划也印证了这一点：
```
SCAN entry USING INDEX idx_entry_date
CORRELATED SCALAR SUBQUERY 1
SCAN a
```
**是 `SCAN`（全扫）不是 `SEARCH`（按范围定位）**。

**为什么不修**：彻底修要给 `entry` 加一列持久化的 `has_content`（写入时维护），
那就是 **schema v4 ＋ 迁移 ＋ 改所有写入路径** ——
为一个"要写 59 年才能遇到"的场景动核心表结构，风险大于收益。
（用户 2026-09-30 的判断：*"谁家好人能写 10 万篇"*。）

### 灾难线参考（10 万篇 ≈ 297 年，**不是需求**）

顺手跑过一组留档：列表 214ms ／ 搜索 213ms ／ **统计 6520ms** ／ 日历 78ms ／
筛选 1565ms ／ 体检 2030ms —— 统计页 6.5 秒。**跑得出，但现实到不了。**
