## 三、⚠️ 本批两次"判据自己被抓红"（都留着，这是证据）

### ① 我自己的自测把 `diffImages` 的用例写错了

`selfTest` 里用棋盘图验"容差"：隔行差 3 级 ⇒ **只有一半像素变了**，
可我第一版断言写的是"容差 0 时该数出 **全部** `W×H` 个"。脚本第一次跑**直接在这一条上退出**（`EXIT=3`），
说明 `selfTest` 真的在挡事 —— 不写这一段，我会一直以为容差逻辑是对的。

### ② ⭐⭐ K13 第一版是**假绿**

第一版写的是"把 dpr 拉到 3，再读 `pixelRatio` 是不是 ≤ 2"。它**通过了**，但读到的仍是 **1.875** ——
因为 `renderer.setPixelRatio(min(dpr, 2))` **只在组件挂载时调一次**，
改 `deviceScaleFactor` 根本不会让它重算。⇒ **把封顶那行代码整个删掉，那条断言照样绿。**
修法：让组件在 **dpr ＝ 3 的状态下重新挂载**（切到「刻度」再切回「树语」），
这样 `setPixelRatio(min(3, 2))` 才会真的跑一遍、真的被封到 2。

⭐ **顺带发现一个已知边界**（⚠️ **没有动代码，报给你定**）：
窗口被拖到**另一块缩放比不同的显示器**上时 `devicePixelRatio` 会变，但 `setPixelRatio` 不会重跑 ⇒
画布不会按新密度重算。补法是把它挪进 `resize()`（一行），代价是**每一批都要重跑一次界面验收**。
本次跑完的 `验收结果.json` 里有 `K_dpr_note` 这一条信息行，原文记着这件事。

### ③ `drawCalls` 那条断言也是我猜错的

第一版断言"这一帧画 **3** 次（树干＋叶＋花）"，实测是 **8** —— 因为 `renderer.info.render.calls`
**把阴影通道也算进去**，而阴影通道里有几个物体投影取决于各自的 `castShadow`。
⇒ 改成只断言一个**结构上一定成立**的下限（≥ 5，主通道那 5 个 mesh），
**并把"三角形预算逐个数得上"（I3）当成真正的硬证据** —— 那条是算出来的，不是猜的。

## 六、怎么复跑

```powershell
# 1. 先构建（前端资源是编译进 exe 的，不重编就还是旧前端）
cd app; node node_modules/vite/bin/vite.js build
cd ..; cargo build --release --features custom-protocol

# 2. 跑界面验收（约 1 分钟；会自动起 exe、连 CDP、拍 8 张图）
node "生产\交付证据\树语-第1期-花叶\验收脚本.cjs"
```

- 默认验 `target\release\app.exe`；用 `DIARY_EXE` 环境变量可以指到发布件。
- 一次性数据目录 `_probe-tree-3\`（已被 `.gitignore` 的 `_probe-*/` 挡住）。
- 端口 **9336**（批次 1 用 9334、批次 2 用 9335，每版都换，别撞）。
- 结果落在 `_probe-tree-3\probe-result.json`，本目录下的 `验收结果.json` 是它的归档副本。
- ⚠️ 跑之前**关掉正在运行的日记**（残留 WebView2 进程会让调试端口**静默失效**）；
  脚本里已带 `killLeftovers()`，且开局会清 `localStorage`。
