## 一、这一件是什么

**改之前**：搜一个词，结果里**只有第一处**标黄 —— 一篇日记里那词出现八次，只亮一处。
根因是 `SearchPanel.parts()` 里一行 `indexOf`（它天生只找第一处）。

**改之后**：**所有出现的地方都亮**，而且**多个词分别亮**（搜「青柠 绿茶」两个都亮）。

**改动面（极小）**：

| 文件 | 改什么 |
|---|---|
| `app/src/utils/text.ts` | 新增 `Seg` ＋ `splitByTerms()`（纯函数，抽出来才能写单测） |
| `app/src/components/SearchPanel.vue` | `parts()` 改成调它 ＋ 一个 `terms()` 取词函数 |
| `app/tests/text.test.ts` | **新建** —— 14 条前端单测（Node 自带测试器，零新依赖） |
| `app/package.json` | 加一行 `test:fe` 脚本 ＋ 版本号 → `3.15` |
| `app/src/utils/text.ts` | 顺带把 `./richText` 的 import 补上 `.ts` 后缀（Node 的 ESM 不认无扩展名） |

⚠️ **后端零改动**：`db::make_snippet()` 早在 `3.13` 就 `strip_html()` 过了
⇒ 摘要本来就是纯可见文字，前端在它上面找词天然正确。

## 四、这一轮踩到的三个坑（都值得留下）

### 1. ⭐⭐ 「等结果出现」等到的是**上一轮的结果**

第一版 `searchAndRead()` 只做了"等 `.item-snippet` 出现"。问题是
`SearchPanel.run()` 是**异步**的（等 IPC 回来才换 `results`），
在这期间**上一轮的 DOM 还在** ⇒ "等结果出现"**立刻**满足 ⇒ 读到陈旧数据。
第一次跑因为时序凑巧躲过去，第二次直接红了三条。

**修法**：搜之前**先清空、亲眼看结果区空掉**，再搜、再等 —— 也就是本项目的**铁律 13**：
> 等某个界面状态变了，必须**亲眼看它经过中间态**。

### 2. 用例设计错了 ≠ 产品错了（但也要看出来）

「有结果、但一处都不亮」这条，第一版我拿「`青柠 zzz不存在zzz`」去造 ——
结果**返回 0 条**（后端那张表是**词 AND ＋ 单字 AND**，多一个不存在的词就全不匹配）。
改成「让两个查询词都落在**第 40 字之后**」（后端的 `make_snippet` 拿**整个查询串**找位置、
找不到就从第 0 字开窗）⇒ 有结果、窗口里一个查询词都没有 ⇒ 稳定复现。

### 3. ⚠️ Bash 双引号里的**反引号**会当命令替换执行

用 `python -c "…"` 打补丁时，我注释里的 `` `SearchPanel.run()` `` / `` `.item-snippet` ``
被 bash 当成命令替换**执行并替换成空**，注释被吃掉两行（代码本体没事）。
**教训：凡是要写进文件的文本里有反引号，就用 Write/Edit 工具或写成 `.py` 文件跑，
⛔ 不要塞进 `bash -c "…"` 的双引号里。**
